# 우하단 액션 독 (Action Dock) — SpinX 허브 통합 설계

> 상태: 설계 확정 (구현 1단계 = BudgetOpt 결과 화면)
> 배경: BO 결과 화면의 "Reach Caster 연계 CTA"를 어디에 둘지 검토하다, 우하단 플로팅 요소가
> 기능 증가에 따라 난잡해지는 구조적 문제를 발견. 개별 플로팅을 늘리는 대신 **우하단을 하나의
> 액션 허브(독)로 통합**하기로 결정.

---

## 1. 문제 정의

- 결과 화면 우하단에 플로팅 요소가 제각각 늘어난다: SpinX 버튼, (Reach Caster) 시나리오 비교 버튼,
  이번에 추가한 "도달 예측" CTA pill 등.
- 플랫폼이 커질수록 화면별 부가기능이 늘고, 그때마다 플로팅을 하나씩 더 붙이면 우하단이 난잡해진다.
- UI 원칙(강조는 한 곳 / 플로팅 겹침 회피)과 정면으로 충돌.

## 2. 해결 방향 — 하나의 "액션 독"으로 수렴

우하단을 **SpinX 입력 바(메인) + ＋ 액션 런처(보조)** 한 묶음으로 통합한다.
개별 플로팅(비교 버튼, 도달예측 pill)은 모두 이 독으로 흡수한다.

ReadySet 철학("경계 없는 단 하나의 세션")과 정합: 독이 **"지금 이 화면에서 이어서 할 수 있는 것"의 관문**이 된다.

---

## 3. 확정된 UX (목업 합의 완료)

### 3.1 상태
1. **기본** — 좁은 SpinX 입력 바 + 그 위 작은 ＋. 우하단 깔끔.
2. **입력 포커스** — 입력 바에 그린 포커스 링, **추천 질문이 위로 펼쳐짐**(평소엔 숨김, 공간 절약).
3. **＋ 열림** — ＋가 ×로 **회전**, 액션들이 **알약(pill)으로 위로 쌓여 떠오름**(speed dial). 별도 팝오버 창 없음.

### 3.2 액션 알약
- **라벨 + 아이콘 상시 노출** (직관성 우선). 아이콘-only + hover 라벨 방식은 채택하지 않음.
- 위로 쌓기. 아이콘은 우측 정렬(＋ 버튼과 세로 정렬).
- 등장은 아래→위 순차(stagger), 모션은 미세하게(~0.2s). 부양/그림자 확대 없음.

### 3.3 위계
- **SpinX 입력 바 = 메인, ＋ = 보조 런처.** 둘을 같은 강도로 강조하지 않는다.
- **그린(시그니처 강조색) 분배는 홀딩(미정).** 구현 시 별도 결정. 일단 무채색 기조로 두고, 그린 적용 지점은
  추후 "시스템이 짚은 핵심 액션 한 곳"에만 얹는 방향으로 검토.

### 3.4 화면별 액션 예시
- **BudgetOpt 결과**: 도달 예측하기 (현재 1개, 확장 대비 설계)
- **Reach Caster 결과**(향후): 시나리오 비교, 업종 데이터 뽑기 등

---

## 4. 아키텍처 — 공용 독 + 컨텍스트 액션 레지스트리

핵심: 독은 **렌더만** 하고, "무슨 액션이 있는가"는 **각 화면이 주입**한다. 그래야 화면/솔루션마다 다른 액션을
꽂을 수 있고, 신규 기능은 목록에 등록만 하면 된다.

### 4.1 액션 타입(안)
```ts
interface DockAction {
  id: string
  label: string              // 알약에 보일 라벨 (예: "도달 예측하기")
  icon: ReactNode            // lucide 아이콘
  onSelect: () => void       // 클릭 시 동작 (예: 모달 열기)
  emphasis?: boolean         // 핵심 액션 여부 (그린 적용 후보) — 그린 홀딩이라 당장은 미사용
}
```

### 4.2 독 컴포넌트(안)
```ts
// 공용 컴포넌트. SpinX 입력 바 + ＋ 액션 런처를 한 묶음으로 렌더.
interface ActionDockProps {
  actions: DockAction[]            // 화면이 주입하는 컨텍스트 액션 목록
  spinx: { /* 기존 SpinX 패널 열기/추천질문 등 연동 */ }
}
```
- `actions`가 비면 ＋ 런처는 숨긴다(빈 메뉴 방지).
- 독은 SpinX 입력 바의 포커스→추천질문, ＋→알약 스택 두 상호작용만 관리.

### 4.3 모듈 경계 (핸드오프 가이드 준수)
- **공용 독 컴포넌트**는 공통 성격 → 신규 공통 위치에 둔다(예: `src/components/common/` 또는
  독 전용 폴더). budgetoptimizer 전용으로 가두지 않는다(향후 Reach Caster 재사용 목적).
- **SpinX 입력 바 전환**: SpinX(`SpinXButton`/`SpinXPanel`)는 Reach Caster와 **공용**이다.
  입력 바화는 공용 컴포넌트에 영향을 주므로, **BO부터 붙이되 공용으로 설계(B안)**.
  Reach Caster 화면은 1단계에서 건드리지 않는다 → 1단계에서는 화면 간 SpinX 호출부 모양이 잠시 다를 수 있음(허용).
- 핸드오프상 slot/reachcaster/datashot/spinx는 신중 모듈. SpinX 입력 바 전환이 spinx 모듈 변경을 수반하면,
  **기존 SpinXButton/Panel의 공개 동작(열기/추천질문/세션)을 깨지 않는 선**에서 호출 표면만 확장한다.

## 5. 단계 적용안

### 1단계 — BudgetOpt 결과 화면 (지금)
1. 방금 만든 **도달예측 collapsed pill 롤백/흡수**: `BOReachEdgeTab`은 독의 액션으로 대체되므로 제거한다.
   (BOResult.tsx의 해당 렌더/상태 정리. 헤더 ghost 버튼은 이미 제거됨 — 변경 없음.)
2. 공용 **ActionDock** 신설 (SpinX 입력 바 + ＋ 알약 스택).
3. BO 결과 화면이 `actions=[{ 도달 예측하기 → setEasyCreateOpen(true) }]`를 주입.
4. SpinX 연동: 기존 SpinX 패널 열기/추천질문을 독의 입력 바에서 호출.
5. 검증: 우하단에 플로팅이 "독 하나"로만 보이는지, SpinX 기능 회귀 없는지.

### 2단계 — Reach Caster 결과 화면 (향후)
- 같은 ActionDock을 Reach Caster 결과/비교 화면에 붙이고, 기존 "시나리오 비교" 버튼을 액션으로 흡수.
- "업종 데이터 뽑기"(DataShot 연계) 등 추가 액션 등록.

### 3단계 — 플랫폼 공통화 (향후)
- 신규 솔루션/화면은 `actions` 주입만으로 독에 부가기능 노출.

---

## 6. 보류/후속 결정
- **그린 적용 지점** — "핵심 액션 한 곳"에만 얹을지, 아예 무채색으로 갈지. 1단계 구현 후 실물 보고 결정.
- **＋와 입력 바 물리 배치** — 세로 스택(＋ 위) 확정. 가로 나란히는 미채택.
- **추천 질문 노출** — 입력 포커스 시에만 펼침 확정.

---

## 7. 원칙 체크
- 강조 한 곳: SpinX 입력 바(메인) 하나. ＋는 보조. (그린 홀딩)
- 플로팅 겹침 회피: 개별 플로팅을 독 하나로 수렴 → 겹침 문제 소멸.
- 토큰만 사용, HEX 금지, 미세 모션 — 구현 시 핸드오프/디자인 가이드 준수.
