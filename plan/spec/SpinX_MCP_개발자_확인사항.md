## 1. 우선 확인 (정책 확정에 필수)

### Q1. 승인 후 함수 변경 처리
> [확정] 모니터링 프로세스가 승인된 MCP 변경을 감지 → 상태를 **`pending`으로 회귀** → App 관리자에게 이메일 알림 → 재심사·재승인.
- (draft 단계에서는 여기까지로 충분. 세부는 구현 확정 후 보완)

### Q2. 블랙리스트(`deny`) 모드 신규 함수 처리
- deny 모드로 승인된 서버에 원격 함수가 **새로 추가**되면, 15분 폴링(`ToolsInterval`) 시점에 **자동으로 노출**되나요?
- 이때 `needs_review`가 걸리나요, 아니면 심사 없이 바로 활성화되나요?
- (보안상 가장 중요한 항목)

### Q3. 거부·재요청 규칙
- 거부된 서버를 재요청할 때 이전 `reason`(거부 사유)이 **앱 사용자에게 노출**되나요?
- 재요청 **횟수 제한**이 있나요? 없다면 무제한 재요청 가능한 상태인가요?

### Q4. suspended 자동 복귀
- `suspended` → 재연결 성공 시 `approved`로 자동 복귀할 때, 그 사이 **함수가 변경됐다면** `needs_review`가 함께 걸리나요?
- 자동 복귀 시 관리자에게 별도 통지가 있나요?

## 2. 추가 확인 (UX·운영)

### Q5. 상태 노출 / 알림
> [1차 확인됨] App 관리자가 요청 시 **이메일**을 함께 등록 → 상태 변경을 해당 이메일로 통지.
- 확정 필요: 통지되는 **상태 이벤트 범위**는? (ai_reviewed / approved / rejected / pending 회귀 / suspended 전부인가?)
- 이메일 외 채널(슬랙 등) 계획이 있나요?
- 이메일은 요청 건마다 1개인가요, 앱 단위로 고정인가요?

### Q6. 함수 전량 거부 케이스
- AI 심사에서 **모든 함수가 rejected** 되면 서버 상태는 어떻게 되나요? (`ai_reviewed`로 넘어가되 노출 함수 0개 상태인지, 자동 반려인지)

### Q7. 타임아웃·실패 처리
- 등록 시 연결 테스트와 `inspect`(30초)의 **실패 시 반환 메시지/코드**가 정의돼 있나요? 사용자 안내 문구 커스터마이징 가능 여부.

### Q8. 권한 주체
- "관리자"는 어떤 **역할/등급**인가요? 앱 담당자와 승인 관리자가 **분리**되어 있나요?
- 관리자 API(`/mcp`)의 인증·인가 방식은? (앱 API는 API Key 인증으로 명시됨)

### Q9. AI 심사 기준
- AI 1차 심사 프롬프트의 **판정 기준을 기획에서 조정** 가능한가요? (기준표를 정책서에서 정의해 반영할 수 있는지)
- 배치 크기(20개), 폴링 주기(Ping 1분 / Tools 15분) 등은 **설정값**인가요, 하드코딩인가요?

### Q10. 운영용 화면(UI) 유무
- 현재 확인된 것은 **API 테스트용 화면(포스트맨/스웨거 형태)** 뿐이며, 일반 앱 담당자·관리자가 클릭으로 쓰는 **운영용 UI는 없는 것으로 이해**했습니다. 맞나요?
- 운영용 UI를 **구축할 계획**이 있나요? 있다면 **시점**과 **소속 위치**(SpinX 자체 어드민 / adly / 별도 콘솔)는?
- 관리자 승인은 **화면에서 처리**할 계획인가요, 아니면 **알림(메일/슬랙 등) 수신 후 API로 처리**하는 방식인가요?
- UI가 없는 동안 앱 담당자의 등록·승인 요청은 **어떤 방식**으로 받나요? (직접 API 호출 / 요청서 접수 / 담당자 대행 등)
