## Executive Summary

**ReadySet 플랫폼에 SpinX와 함께 일하는 모드(WithSet)를 더해, 솔루션 모음에서 쓸수록 똑똑해지는 플랫폼으로 전환함.**

WithSet에서는 SpinX가 렙사의 분석 지식과 솔루션을 엮어 근거 있는 판단·제안·검증을 수행하고, 그 결과가 플랫폼에 누적되는 자산이 됨. 솔루션을 **직접 다루는 ReadySet**과 **함께 일하는 WithSet**은 GNB 로고와 별도 진입점에서 전환함 (상세: WithSet 한눈에 보기)

### 1. 추진 배경 및 필요성

- 매체 AI의 집행 자동화(입찰·타겟·소재 배분) 확산 → 렙사의 집행 대행 가치 축소, 역할이 **매체 간 판단과 검증**으로 이동
- 렙사의 핵심 자산은 여러 광고주·여러 매체의 집행 데이터와 이를 검증한 분석 → 그러나 메일·사내 기간계에 흩어져 있어 활용 불가
- 현재 ReadySet 솔루션(DataShot, BudgetOpt 2.0, Reach Caster)은 Slot 단위로 직렬 운영 → 솔루션 간 결과를 엮어 하나의 산출물로 만드는 구조 부재
- 2027년 1~2월 Ad Curator 출시로 상품 추천 → 예산 배분 → 도달 예측의 3개 솔루션이 갖춰짐 → 솔루션 연결 시점 도래

### 2. 핵심 전략

| 축 | 전략 | 내용 |
|---|---|---|
| Knowledge | 지식 베이스 구축 | 공통 기준(시맨틱 · 온톨로지) 정의, 데이터 사이언스(DS) 분석 · 매체 소식 구조화 축적 |
| Intelligence | SpinX 근거 인용 + WithSet Chat | 전 솔루션 SpinX가 지식 베이스로 결과 해석, WithSet Chat에서 시나리오 진단 |
| Agent | Workflows + Skills | 자연어 요청 → 솔루션 연결 → 제안셋 생성, 작성 방법(Skills) 저장·재사용 |
| Data | Tools (MCP 연결) | 매체 · 사내 · 외부 MCP를 하나의 구조로 연결, 매체 실측으로 예측 보정 |
| Supply | MCP 공급 | 축적된 솔루션·지식·Skills를 외부 LLM에 공급 |

## WithSet 한눈에 보기

### 1. 브랜딩 — 하나의 플랫폼, 두 개의 모드

| 구분 | ReadySet — 직접 다루는 곳 | WithSet — 함께 일하는 곳 |
|---|---|---|
| 일하는 방식 | 사용자가 솔루션을 직접 다룸 | SpinX에게 맡기고 함께 처리 |
| 단위 | 캠페인(Slot) 하나, 솔루션 하나씩 | 요청 하나. Slot과 솔루션을 넘나듦 |
| 입력 | 화면에서 조건을 입력하고 실행 | 말로 요청하면 렙사 지식과 솔루션을 엮어 처리 |
| 남는 것 | 시나리오 | Artifacts · Workflows · Skills |
| 대표 화면 | SlotBoard, DataShot · BudgetOpt 2.0 · Reach Caster · Ad Curator | Home(질문), Library, Artifacts, Workflows, Skills, Tools |

- **이름**: Set은 ReadySet 패밀리를 잇고, With는 **SpinX와 함께 · 렙사의 지식과 함께 · 팀과 함께** 일한다는 의미
- **전환 방식**: GNB 로고에서 "Set"은 고정, 앞 단어만 Ready ⇄ With로 바뀌어 두 모드임을 드러냄. 로고 외 별도 진입점도 제공 (위치·형태는 기획 과정에서 확정)
- **위계**: WithSet은 별도 제품이 아닌 ReadySet 플랫폼의 모드. 외부 표기는 "ReadySet의 WithSet"

### 2. 구조 — 요청이 결과가 되기까지

```
Chat  →  SpinX  →  Skills/Library/Solutions/Tools  →  Artifacts
```
- **Chat**: 말로 요청
- **SpinX**: 요청을 해석하고 필요한 것을 골라 씀
- **Skills**: 어떻게 만들지 (방법)
- **Library**: 무엇을 근거로 (지식)
- **Solutions**: Ad Curator · BO 2.0 · RC
- **Tools**: 매체 · 사내 · 직접 등록 MCP
- **Artifacts**: 결과 (제안셋 · 메모 · 비교)
- **Workflows** — 위 과정의 순서. 실행하면 자동으로 기록되고, 이벤트·스케줄로 다시 실행
- 공통 기반: 시맨틱 레이어(지표 · 용어 · 규칙) · 온톨로지(엔티티 · 관계) · 접근제어(slotScope · audienceLevel)

| 구성 | 한 줄 정의 | 사용자에게 보이는 방식 |
|---|---|---|
| Chat | 일을 시키는 곳 | 어느 화면에서든 SpinX 패널. 대화는 개인 기록으로 남음 |
| Skills | 일하는 방법 | 대화 답에서 "Skill로 저장". SpinX가 요청에 맞는 Skill을 골라 씀 |
| Workflows | 일의 순서 (반복) | 대화에서 실행하면 자동 기록. 캔버스는 확인 · 수정용 |
| Artifacts | 일의 결과 | 만든 곳 · 사용한 Skill · 근거와 함께 보관 |
| Library | 근거 지식 | 분석 리포트 · 매체 소식 |
| Solutions | 계산하는 엔진 | Ad Curator · BudgetOpt 2.0 · Reach Caster. ReadySet에서 직접, WithSet에서는 SpinX가 이어서 실행 |
| Tools | SpinX가 쓰는 도구 (MCP) | 매체 · 사내 · 외부 MCP를 하나의 구조로 연결. 매체(실측) · 사내(기간계 · Slack · Drive 등) · 외부(사용자 직접 등록) |

### 3. 대표 유즈케이스 — 캠페인 하나로 이어지는 세 장면

예시 캠페인: 삼성 갤럭시 2027 추석 프로모션 (BudgetOpt 2.0 · 클릭 KPI · 증액 · 신상품 출시)

| # | 장면 | 사용자 요청 | WithSet이 하는 일 | 쓰는 기능 | Phase |
|---|---|---|---|---|---|
| 1 | **분석 리포트로 시나리오 진단** | "갤럭시 2027 추석 프로모션, 연휴에 증액해도 괜찮을까?" | 시나리오 조건(장기 연휴 · 컴퓨터·IT · 증액)에 맞는 발견을 찾아 근거와 함께 판단 제시 | Library, SpinX | 1 |
| 2 | **제안셋 만들기** | "이 근거로 광고주 제안셋 만들어줘" | Ad Curator → BudgetOpt 2.0 → Reach Caster를 이어 실행하고, Skill로 광고주 설명 자료 작성 | Skills, Workflows, Artifacts | 2 |
| 3 | **실측 성과와 비교** | "작년 추석 집행 성과랑 이 시나리오 비교해줘" | 매체 MCP로 실측을 가져와 예측과 대조하고, 시장 요인과 운영 요인을 분리해 보정 방향 제시 | Tools, Library | 3 |

- 장면 3의 비교 결과는 다음 시나리오를 진단할 때 근거로 다시 쓰임 → **쓸수록 판단이 정확해지는 구조**
- 실측이 연결되면 그간 시나리오와 이어지지 않던 "성과 해석" 리포트가 처음으로 연결됨
- 목업의 수치는 예시 데이터임

## 1. 배경 (Background)

### 1.1 사업 환경 (Business Context)

- 당사는 매체 공식 렙사로, 그간 핵심 가치는 매체 집행 대행과 운영 노하우
- 매체별 AI 자동 최적화(Meta Advantage+, Google PMax 등) 확산 → 단일 매체 내 집행·최적화는 매체가 직접 수행
- 매체 AI는 자기 매체 안에서만 최적화 → **매체를 가로지르는 예산 판단, 여러 광고주의 실측 비교, 검증된 해석**은 매체·광고주 모두 단독 수행 불가
- 범용 LLM 확산으로 화면·기능 단위 경쟁력 약화 → 렙사만 보유한 데이터와 방법론의 자산화가 경쟁력의 원천

### 1.2 현황 (Current State)

- ReadySet 솔루션은 Slot(광고주·캠페인) 하위에서 개별 실행 → 솔루션 간 맥락 전달은 BudgetOpt 2.0 → Reach Caster 연결 수준
- 데이터 사이언티스트 분석 결과를 내부 사용자 대상 뉴스레터 파일럿으로 발송하는 방안 검토 중 (미발송) → 목적은 지식 베이스 축적
- 매체 프로모션·신상품 정보는 사내 기간계에 존재하나 양식이 통일되지 않음

### 1.3 문제 정의 (User Problems) & 기회 요인 (Opportunities)

| # | User Problems | Opportunities |
|---|---|---|
| 1 | **지식의 휘발**<br>분석 결과가 메일로 1회 소비되고 종료 → 축적·검색·재활용 불가. 매체 소식은 양식이 제각각이라 검색·매칭 불가 | **[Knowledge] 지식 자산화**<br>분석·매체 소식을 공통 스키마로 구조화하여 누적 가능한 지식 베이스로 전환 |
| 2 | **결과 근거 부족**<br>솔루션 결과에 "왜 이 배분인가"에 대한 외부 검증 근거가 붙지 않아 제안 설득력 한계 | **[Intelligence] 근거 기반 해석**<br>SpinX가 결과 해석 시 지식 베이스의 검증된 분석을 근거로 인용 |
| 3 | **솔루션 간 단절**<br>제안셋 1건 작성을 위해 Ad Curator, BudgetOpt 2.0, Reach Caster를 각각 실행하고 결과를 수작업 취합 | **[Agent] 요청 단위 자동화**<br>자연어 요청 1건으로 솔루션을 연결 실행하고 근거까지 포함한 제안셋 생성 |
| 4 | **반복 프롬프팅**<br>동일 유형 산출물(예: 광고주 대상 설명 자료)도 매번 지시를 새로 작성 | **[Agent] Skills**<br>산출물 작성 방법을 패키지로 저장하여 재사용 |
| 5 | **예측-실측 단절**<br>시나리오와 실제 집행 결과의 대조가 플랫폼 밖에서 수작업으로 진행 | **[Data] 실측 결합**<br>매체 MCP 연동으로 시나리오 대비 실측 비교, 예측 보정 근거 축적 |
| 6 | **기준의 불일치**<br>지표 계산 방식, 매체·업종 용어, 연휴 구분 기준이 분석·솔루션·매체 소식마다 달라 매칭과 인용 결과를 신뢰하기 어려움 | **[Knowledge] 공통 의미 기준**<br>시맨틱 레이어로 지표·용어·규칙을, 온톨로지로 엔티티 간 관계를 단일 기준으로 정의 |

## 2. 목적 (Purpose)

Slot 단위 직렬 솔루션 구조에서 벗어나, 렙사 고유 지식과 솔루션이 사용할수록 누적·연결되는 플랫폼 구조를 구축하는 것을 목적으로 함

- **지식 자산화**: 분석·매체 소식을 축적하여 전 솔루션의 해석 근거로 활용
- **솔루션 오케스트레이션**: 솔루션을 연결 실행하여 요청 단위 산출물 생성
- **공급 기반 확보**: 축적된 자산을 외부 LLM에 공급할 수 있는 구조 마련

- K1·K2 v0은 매칭·인용에 실제 사용하는 항목으로 한정하고 사용 범위에 따라 확장
- K1 지표 정의는 BudgetOpt 2.0·Reach Caster 계산 기준과 일치해야 함
- 플랫폼에는 분석 내용만 반영. 뉴스레터 파일럿의 캐릭터·레이아웃은 메일 채널에서만 사용
- 콘텐츠 규모는 건수가 아닌 **업종 × 시즌 × 매체 × KPI 조합 커버리지** 기준으로 관리. 현재 논의 규모(15건)로는 근거 공백 다수 발생 → 분석 결과 양산 파이프라인 검토 중

### 5.3 Phase 3·4 — Tools(MCP 연결) · MCP 공급

- **Phase 3**: 광고주별 매체 MCP 연동, 시나리오-실측 비교 요청 처리. 연동 전 토큰 격리·권한 정책 수립 선행
- **Tools — MCP 연결 구조**: 매체 MCP · 사내 MCP · 외부 MCP를 모두 하나의 연결 구조로 수용
  - 매체 MCP: 광고주(Slot) 단위 연결, 실측 성과 수집
  - 사내 MCP: 기간계 · Slack · Google Drive 등, 관리자가 일괄 제공
  - 외부 MCP: 사용자가 직접 등록. 개인 범위로 시작, 팀 공유 시 관리자 검토
  - 공통 정책: 외부 도구 호출 시 매번 사용자 승인, 권한 범위 내 데이터만 전송, 임직원 전용 자료 전송 차단
- **Phase 4**: 솔루션·지식·Skills의 MCP 공급. 공급 대상 자산이 Phase 1~3에서 축적된 이후 추진
