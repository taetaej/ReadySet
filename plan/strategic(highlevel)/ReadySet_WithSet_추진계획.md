## Executive Summary

**ReadySet 플랫폼에 AI Agent 협업 레이어(WithSet)를 더해, 개별 솔루션의 묶음에서 사용할수록 판단이 정교해지는 플랫폼으로 전환함.**

- **왜 지금인가**: 매체 AI의 집행 자동화로 렙사의 가치가 집행 대행에서 매체 간 판단·검증으로 이동하고 있으며, 2027년 1~2월 Ad Curator 출시로 상품 추천 → 예산 배분 → 도달 예측의 솔루션 체계가 완성됨
- **무엇을 하는가**: 렙사가 축적한 분석·매체 소식을 지식 자산으로 구조화하고, SpinX가 이 지식과 솔루션을 엮어 근거 있는 판단·제안·검증을 수행하는 협업 레이어(WithSet)를 구축함
- **무엇이 달라지는가**: 판단의 근거가 개인 경험에서 플랫폼 자산으로 옮겨가고, 사용 결과가 다시 지식으로 축적되는 선순환 구조가 만들어짐
- **어떻게 경험하는가**: 솔루션을 **직접 다루는 ReadySet**과 SpinX와 **함께 일하는 WithSet**을 하나의 플랫폼 안에서 GNB 로고와 별도 진입점으로 전환함 (상세: WithSet 한눈에 보기)

### 1. 추진 배경 및 필요성

- **역할 재정의 요구**: 매체 AI의 집행 자동화(입찰·타겟·소재 배분) 확산으로 집행 대행 가치가 축소되고, 렙사의 역할이 **매체 간 판단과 검증**으로 이동
- **미활용 핵심 자산**: 여러 광고주·매체의 집행 데이터와 이를 검증한 분석은 렙사만의 자산이나, 메일·사내 기간계에 흩어져 활용되지 못함
- **솔루션 간 단절**: DataShot, BudgetOpt 2.0, Reach Caster가 Slot 단위로 각각 운영되어, 솔루션 결과를 하나의 산출물로 엮는 구조가 부재
- **연결 시점 도래**: 2027년 1~2월 Ad Curator 출시로 상품 추천 → 예산 배분 → 도달 예측의 체계가 갖춰져, 솔루션 연결의 실익이 처음으로 확보됨

## WithSet 한눈에 보기

### 1. 브랜딩 — 하나의 플랫폼, AI Agent 협업 레이어

| 구분 | ReadySet — 직접 다루는 곳 | WithSet — 함께 일하는 곳 |
|---|---|---|
| 일하는 방식 | 사용자가 솔루션을 직접 조작 | SpinX에게 맡기고 함께 판단 |
| 작업 단위 | 캠페인(Slot) · 솔루션 단위 | 요청 단위. Slot과 솔루션을 가로지름 |
| 입력 | 화면에서 조건을 입력하고 실행 | 자연어로 요청하면 렙사 지식과 솔루션을 엮어 처리 |
| 축적 자산 | 시나리오 | Artifacts · Workflows · Skills |
| 대표 화면 | SlotBoard, DataShot · BudgetOpt 2.0 · Reach Caster · Ad Curator | Home(질문), Library, Artifacts, Workflows, Skills, Tools |

- **이름**: Set은 ReadySet 패밀리를 잇고, With는 **SpinX와 함께 · 렙사의 지식과 함께 · 팀과 함께** 일한다는 의미
- **전환 방식**: GNB 로고에서 "Set"은 고정하고 앞 단어만 Ready ⇄ With로 전환하여, 같은 플랫폼 안의 화면 전환(모드)임을 드러냄. 로고 외 별도 진입점도 제공 (위치·형태는 기획 과정에서 확정)
- **위계**: WithSet은 별도 제품이 아닌 ReadySet 플랫폼 위의 AI Agent 협업 레이어. 화면에서는 모드로 전환하며, 외부 표기는 "ReadySet의 WithSet"

### 2. 구조 — 요청이 결과가 되기까지

```
Chat  →  SpinX  →  Skills/Library/Solutions/Tools  →  Artifacts
```
- **Chat**: 자연어로 요청
- **SpinX**: 요청을 해석하고 필요한 지식 · 방법 · 솔루션 · 도구를 선택해 실행
- **Skills**: 어떻게 만들 것인가 (방법)
- **Library**: 무엇을 근거로 할 것인가 (지식)
- **Solutions**: Ad Curator · BO 2.0 · RC
- **Tools**: 매체 · 사내 · 직접 등록 MCP
- **Artifacts**: 결과 (제안셋 · 메모 · 비교)
- **Workflows**: 위 과정의 실행 순서. 실행 시 자동 기록되고, 이벤트 · 스케줄로 재실행
- **공통 기반**: 시맨틱 레이어(지표 · 용어 · 규칙) · 온톨로지(엔티티 · 관계) · 접근제어(slotScope · audienceLevel)

| 구성 | 정의 | 사용자 경험 |
|---|---|---|
| Chat | 업무 요청 창구 | 어느 화면에서든 SpinX 패널로 접근. 대화는 개인 기록으로 보관 |
| Skills | 업무 방법 | 답변에서 "Skill로 저장". SpinX가 요청에 맞는 Skill을 선택해 적용 |
| Workflows | 업무 순서 (반복) | 대화에서 실행하면 자동 기록. 캔버스는 확인 · 수정용 |
| Artifacts | 업무 결과 | 생성 위치 · 사용 Skill · 근거와 함께 보관 |
| Library | 근거 지식 | 분석 리포트 · 매체 소식 |
| Solutions | 계산 엔진 | Ad Curator · BudgetOpt 2.0 · Reach Caster. ReadySet에서는 직접, WithSet에서는 SpinX가 연결 실행 |
| Tools | SpinX의 외부 연결 (MCP) | 매체 · 사내 · 외부 MCP를 단일 구조로 연결. 매체(실측) · 사내(기간계 · Slack · Drive 등) · 외부(사용자 직접 등록) |

### 3. 대표 유즈케이스 — 하나의 캠페인으로 이어지는 진단 · 제안 · 검증

예시 캠페인: 삼성 갤럭시 2027 추석 프로모션 (BudgetOpt 2.0 · 클릭 KPI · 증액 · 신상품 출시)

| # | 장면 | 사용자 요청 | WithSet의 역할 | 활용 기능 | Phase |
|---|---|---|---|---|---|
| 1 | **진단: 분석 리포트로 시나리오 검토** | "갤럭시 2027 추석 프로모션, 연휴에 증액해도 괜찮을까?" | 시나리오 조건(장기 연휴 · 컴퓨터·IT · 증액)에 부합하는 분석 발견을 찾아 근거와 함께 판단 제시 | Library, SpinX | 1 |
| 2 | **제안: 제안셋 생성** | "이 근거로 광고주 제안셋 만들어줘" | Ad Curator → BudgetOpt 2.0 → Reach Caster를 연결 실행하고, Skill로 광고주 설명 자료 작성 | Skills, Workflows, Artifacts | 2 |
| 3 | **검증: 실측 성과 비교** | "작년 추석 집행 성과랑 이 시나리오 비교해줘" | 매체 MCP로 실측을 가져와 예측과 대조하고, 시장 요인과 운영 요인을 분리해 보정 방향 제시 | Tools, Library | 3 |

- 장면 3의 검증 결과가 다음 시나리오 진단의 근거로 재사용됨 → **사용할수록 판단이 정교해지는 구조**
- 실측 연결로 그간 시나리오와 분리되어 있던 "성과 해석" 리포트가 처음으로 판단 근거에 편입됨
- 목업의 수치는 예시 데이터임

## 1. 배경 (Background)

### 1.1 사업 환경 (Business Context)

- 당사는 매체 공식 렙사로, 그간 핵심 가치는 매체 집행 대행과 운영 노하우에 있었음
- 매체별 AI 자동 최적화(Meta Advantage+, Google PMax 등) 확산으로 단일 매체 내 집행 · 최적화는 매체가 직접 수행하는 영역으로 전환
- 매체 AI의 최적화는 자기 매체 안에 한정됨 → **매체를 가로지르는 예산 판단, 여러 광고주의 실측 비교, 검증된 해석**은 매체 · 광고주 어느 쪽도 단독으로 수행할 수 없는 렙사 고유 영역
- 범용 LLM 확산으로 화면 · 기능 단위의 차별성은 약화 → 렙사만 보유한 데이터와 방법론의 자산화가 경쟁력의 원천

### 1.2 현황 (Current State)

- ReadySet 솔루션은 Slot(광고주 · 캠페인) 하위에서 개별 실행되며, 솔루션 간 맥락 전달은 BudgetOpt 2.0 → Reach Caster 연결 수준에 그침
- DS 분석 결과를 내부 사용자 대상 뉴스레터로 발송하는 파일럿을 검토 중이나(미발송), 지식 베이스 축적 구조는 부재
- 매체 프로모션 · 신상품 정보는 사내 기간계에 존재하나 양식이 통일되지 않아 검색 · 활용이 어려움

### 1.3 문제 정의 (User Problems) & 기회 요인 (Opportunities)

| # | User Problems | Opportunities |
|---|---|---|
| 1 | **지식의 휘발**<br>분석 결과가 메일로 1회 소비되고 종료되어 축적 · 검색 · 재활용 불가. 매체 소식은 양식이 제각각이라 매칭 불가 | **[Knowledge] 지식 자산화**<br>분석 · 매체 소식을 공통 스키마로 구조화하여 누적되는 지식 베이스로 전환 |
| 2 | **판단 근거의 부재**<br>솔루션 결과에 "왜 이 배분인가"를 뒷받침할 검증 근거가 없어 제안 설득력에 한계 | **[Intelligence] 근거 기반 해석**<br>SpinX가 지식 베이스의 검증된 분석을 근거로 인용하여 결과를 해석 |
| 3 | **솔루션 간 단절**<br>제안셋 1건을 위해 Ad Curator, BudgetOpt 2.0, Reach Caster를 각각 실행하고 결과를 수작업 취합 | **[Agent] 요청 단위 실행**<br>자연어 요청 1건으로 솔루션을 연결 실행하고 근거를 포함한 제안셋 생성 |
| 4 | **노하우의 개인 의존**<br>동일 유형 산출물(예: 광고주 대상 설명 자료)도 매번 지시를 새로 작성하여 품질이 작성자에 좌우됨 | **[Agent] Skills**<br>검증된 작성 방식을 패키지로 저장하여 팀 단위로 재사용 |
| 5 | **예측-실측 단절**<br>시나리오와 실제 집행 결과의 대조가 플랫폼 밖에서 수작업으로 진행되어 예측 개선으로 이어지지 않음 | **[Data] 실측 결합**<br>매체 MCP 연동으로 시나리오 대비 실측을 비교하고 예측 보정 근거를 축적 |
| 6 | **기준의 불일치**<br>지표 계산 방식, 매체 · 업종 용어, 연휴 구분 기준이 분석 · 솔루션 · 매체 소식마다 달라 매칭과 인용 결과를 신뢰하기 어려움 | **[Knowledge] 공통 의미 기준**<br>시맨틱 레이어로 지표 · 용어 · 규칙을, 온톨로지로 엔티티 간 관계를 단일 기준으로 정의 |

## 2. 목적 (Purpose)

Slot 단위로 분절된 솔루션 구조에서 벗어나, 렙사 고유의 지식과 솔루션이 사용할수록 축적 · 연결되는 판단 플랫폼을 구축함

- **지식 자산화**: 분석 · 매체 소식을 축적하여 전 솔루션의 판단 근거로 활용
- **솔루션 오케스트레이션**: 솔루션을 연결 실행하여 요청 단위 산출물 생성
- **공급 기반 확보**: 축적된 자산을 외부 LLM 환경에 공급할 수 있는 구조 마련

## 5. Phase별 주요 요구사항

### 5.1 Phase 1 — 의미 정의 + 지식 베이스 + SpinX 근거 인용 + WithSet 1차 오픈 + 실측 조회

| # | 기능 | 설명 | 우선순위 |
|---|---|---|---|
| K1 | 시맨틱 레이어 | 지표(CPM·CPC·CPV·CTR·VTR·순도달·평균 빈도의 계산식·단위·집계 기준), 차원(업종 분류, 매체·동의어, 매체 유형, KPI), 비즈니스 규칙(연휴 단기·장기, 증액 판단, 매체 비중 기준, 소식 유효기간), 캘린더(연휴·시즌)를 단일 정의로 관리 | P0 |
| K2 | 온톨로지 | 엔티티(광고주·Slot·시나리오·솔루션 결과·매체 / 분석 리포트·발견·조건 / 매체 소식 / Workflow·실행·Artifact)와 관계(발견 → 시나리오 조건 충족, 소식 → 시나리오 적용 기간·매체 일치, 소속, 근거, 실측) 정의 | P0 |
| K3 | 공통 지식 스키마 | DS 분석(개요·가설·결과·시사점·연계 솔루션)과 매체 소식을 공통 스키마로 관리. 발견 단위 조건(업종·기간·매체·KPI·예산)은 K1 기준값 사용 | P0 |
| K4 | 분석 등록 | DS가 구조화 항목에 맞춰 분석 등록. 입력 방식은 DS 협의 후 확정 | P0 |

- **확장 원칙**: K1 · K2 v0은 매칭 · 인용에 실제 사용하는 항목으로 한정하고, 사용 범위에 따라 확장
- **정합성**: K1 지표 정의는 BudgetOpt 2.0 · Reach Caster 계산 기준 및 K10 실측 지표와 일치해야 함
- **실측 연결 전제**: K10 연동 전 토큰 격리 · 권한 정책 수립 선행 (5.3 Tools 공통 정책 적용)
- **채널 분리**: 플랫폼에는 분석 내용만 반영. 뉴스레터 파일럿의 캐릭터 · 레이아웃은 메일 채널에서만 사용
- **커버리지 관리**: 콘텐츠 규모는 건수가 아닌 **업종 × 시즌 × 매체 × KPI 조합 커버리지** 기준으로 관리. 현재 논의 규모(15건)로는 근거 공백이 다수 발생하므로 분석 결과 양산 파이프라인 검토 중

### 5.3 Phase 3·4 — Tools(MCP 연결) · MCP 공급

- **Phase 3**: Phase 1 실측 조회(K10)를 확대하여 연동 매체 · 광고주 확장, 시나리오-실측 비교 · 보정 요청 처리
- **Tools — MCP 연결 구조**: 매체 MCP · 사내 MCP · 외부 MCP를 모두 단일 연결 구조로 수용
  - 매체 MCP: 광고주(Slot) 단위 연결, 실측 성과 수집
  - 사내 MCP: 기간계 · Slack · Google Drive 등, 관리자가 일괄 제공
  - 외부 MCP: 사용자가 직접 등록. 개인 범위로 시작, 팀 공유 시 관리자 검토
  - 공통 정책: 외부 도구 호출 시 매번 사용자 승인, 권한 범위 내 데이터만 전송, 임직원 전용 자료 전송 차단
- **Phase 4**: 솔루션 · 지식 · Skills의 MCP 공급. 공급 대상 자산이 Phase 1~3에서 충분히 축적된 이후 추진
