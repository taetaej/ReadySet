# 2027 ReadySet 프로덕트 방향성 구상

> 상태: **구상 중 (ideas)**. 확정 스펙 아님. 무르익으면 `strategic(highlevel)/`로 승격.
> 작성: 플랫폼 PO 관점. 조직·리소스·계약·가격은 다루지 않는다 (팀장/사업 영역).
> 한 줄: ReadySet은 "캠페인 시작 전 예측하는 도구"에서 **"예측 → 실측 → 교정이 맞물려 도는 닫힌 루프"**로 확장한다.

---

## 0. 이 문서의 위치

AX팀 2027 전략보고(v1.3)에 대응하는 **프로덕트 PO의 방향성 정리**다. 팀 전략 문서가 "외부로 나간다"는 미션·조직·거래 경로를 다룬다면, 이 문서는 그 미션을 **ReadySet이라는 제품이 무엇이 되어야 하는가**로 번역한다.

- 다루는 것: 프로덕트 방향, 레이어 확장, SpinX/DataShot/BO/RC의 진화, 워크플로우·가설검증연구소의 프로덕트 안착
- 다루지 않는 것: 인력 배치, 리소스 이동, 옆 팀 레거시(Opera/Intella 등)의 운명, 가격·계약 — 이건 팀장·사업 결정 사항

---

## 1. 한 문장 — 2027의 ReadySet

> **지금 ReadySet은 "캠페인을 시작하기 전에 예측하는 도구"다.**
> **2027의 ReadySet은 집행 실측을 매체 MCP로 받아 예측과 대조하고, 그 대조가 다음 예측을 정교하게 만드는 "닫힌 루프"가 된다.**

지금 세션은 "캠페인 시작 전"에서 끝난다. 예측을 내놓고 사용자가 판단하면 그걸로 도구의 일이 끝난다. 2027엔 그 세션이 **집행 → 정산 → 다음 캠페인**으로 이어진다. War Room 철학의 "경계 없는 단 하나의 전략 세션"을 캠페인 **종료 후까지** 늘리는 것이다.

---

## 2. 레이어 확장 — 두 번째 루틴의 탄생

지금까지 ReadySet은 **전략 수립 루틴** 하나였다. 4개 솔루션이 캠페인 하나를 관통하는 사전(ex-ante) 예측 흐름이다.

```
[전략 루틴 — 이미 있음]
DataShot(벤치마크) → Ad Curator → Budget Optimizer → Reach Caster
= "캠페인 시작 전, 이렇게 하면 이럴 것이다" (예측)
```

2027엔 여기에 **검증 루틴**이 하나 더 붙는다. 이게 이 문서의 핵심이다.

```
[검증 루틴 — 2027 신설]
집행 실측(매체 MCP) → 예측과 대조 → 편차 + 다음 액션
= "실제로 이렇게 됐고, 예측과 이만큼 달랐다" (실측)
```

두 루틴은 따로 있지 않고 **맞물려 돈다.**

```
        ┌──────────────────────────────────────────────────┐
        │                                                  │
        ▼                                                  │
  [전략 루틴]  DataShot 벤치마크 ─┐                          │
             Budget Optimizer  ─┼─▶ 각자 예측을 남김         │
             Reach Caster      ─┘        │                 │
                                         ▼                 │
                            [검증 루틴]  대조 ──▶ 편차 + 다음 액션
                                         ▲                 │
  실측(매체 MCP) ────────────────────────┘                 │
                                         │                 │
                                         └──▶ 반복 패턴 → 가설검증연구소 → SpinX 학습 ─┘
```

- **대조 대상은 Reach Caster 하나가 아니다.** 전략 루틴 전체가 대조 대상이다.
  - BO 예측(KPI별 배분·효율) ↔ 실제 집행 성과: 배분이 예측대로 효율 났나, CPM은 예측 범위였나.
  - RC 예측(통합 도달·매체 기여) ↔ 실제 도달: 매체별 기여도가 예측대로였나.
  - DataShot 벤치마크(업종 평균) ↔ 이 광고주 실측: 벤치마크가 실제를 담았나 (벤치마크 자체의 정확도 검증).
- 예측이 실측을 부른다. 실측이 다음 예측을 정교하게 만든다 (편차가 쌓이면 업종 벤치마크·모델이 교정된다).
- 이 되먹임이 렙사만의 해자다. 개별 광고주도, 개별 AI 에이전트도 이 루프를 못 돈다. 여러 광고주의 실측을 모을 수 있는 쪽만 돈다.

---

## 3. 두 번째 루틴의 이름 — Performance Tracker

전략 루틴이 캠페인 시작 전 **예측(forecast)**을 다룬다면, 검증 루틴은 집행 후 **실측(actuals)**을 다룬다. 이름은 억지 조어 없이 누구나 바로 읽히는 보편 용어로 잡는다.

> **Performance Tracker** — 매체 MCP로 집행 성과를 추적해, 전략 루틴(DataShot·BO·RC)이 남긴 예측과 대조하는 곳.

Performance Tracker는 특정 솔루션의 하위 기능이 **아니다.** 전략 루틴 여러 솔루션의 예측을 받아 하나의 실측과 맞대는, 한 단계 위의 **공통 대조 레이어**다.

| | 전략 루틴 (DataShot · BO · RC) | Performance Tracker |
|---|---|---|
| 시점 | 캠페인 시작 전 (ex-ante) | 캠페인 집행 중·후 (ex-post) |
| 다루는 것 | 예측 — "이렇게 하면 이럴 것이다" | 실측 — "실제로 이렇게 됐다" |
| 입력 | 사용자 설정(매체·예산·타겟·업종) | 매체 MCP가 가져온 집행 성과 |
| 출력 | 벤치마크·예측 배분·도달·리치커브 | 예측 대비 편차 + 다음 액션 제안 |

다른 솔루션들(DataShot / Ad Curator / Budget Optimizer / Reach Caster)과 나란히 놨을 때 "여러 예측의 성과를 추적·대조하는 곳"으로 한눈에 읽힌다.

> 네이밍은 구상 단계 제안이다. 확정 전까지 치환 가능. (후보: Performance Review, Performance Monitor, Actuals)

## 4. 무엇부터 만드나 — 가치 순서 = 구현 순서

Performance Tracker의 세 조각은 **가치 순위와 구현 난이도가 같은 방향**으로 정렬된다. 그래서 로드맵이 자연스럽다.

### 4-1. 대조의 자동 서사화 (SpinX) — 가장 먼저

- **무엇**: SpinX가 예측·실측 편차를 **업종 맥락으로 설명**한다. 숫자만 던지지 않는다.
  - (예) "A매체가 예측 도달을 밑돈 건 이 업종에서 3분기에 CPM이 계절적으로 오르기 때문. 우리 캠페인은 그 안에서 상위 30%."
- **왜 먼저**: 기존 SpinX 위에 얹으니 진입이 빠르다. ReadySet 정체성(발견의 희열, "나보다 내 캠페인을 잘 아는 파트너")에 가장 직결된다.
- **철학 연결**: ③ 수치 너머의 큐레이션. 대조 결과를 데이터 덤프로 두지 않는 안전장치.

### 4-2. 예측 신뢰도의 제품화 — 대조가 쌓이면

- **무엇**: 예측 대비 실측이 축적되면 업종·매체별 "우리 예측이 얼마나 맞았나"를 정량화. 결과 화면에 은근히 노출.
  - (예) 결과 카드에 "이 업종 도달 예측 정확도 91%" 표기.
- **왜 다음**: 대조 데이터가 한 바퀴 돌아야 나오는 숫자다. 4-1이 선행되어야 재료가 쌓인다.
- **철학 연결**: ④ 모델에 대한 존중 = 근거가 만드는 품격. VIPer(광고주 자사 데이터)는 절대 못 내는 숫자.
- **주의**: 팀 문서 별첨 A의 규율 준수 — 매체 도달 보고값도 추정일 수 있고, 편차를 전부 모델 오류로 돌리지 않는다. "정확도" 표기는 검증된 범위 안에서만.

### 4-3. 상시 모니터링 (워크플로우) — 워크플로우가 성숙하면

- **무엇**: 집행 중 캠페인을 매일 자동으로 끌어와 예측 곡선과 비교하고, 이탈 시 알림.
  - (예) "C매체가 예측보다 15% 부진, 포화 진입 추정 → B로 이전 검토" 를 GNB 알림센터로.
- **왜 나중**: 워크플로우의 스케줄 트리거가 성숙해야 한다. 배치 도구 → 상시 상황판으로 바뀌는 단계.
- **철학 연결**: War Room 상황판. "지금도 새 데이터가 쌓이고 있다"는 살아있는 감각.

```
시간축:  [4-1 서사화] ──▶ [4-2 신뢰도] ──▶ [4-3 모니터링]
근거:    기존 SpinX에      대조가 한 바퀴      워크플로우
         바로 얹음          돌아 쌓인 뒤        스케줄 성숙 후
```

---

## 5. 워크플로우의 정체 — 두 루틴을 잇는 배관

워크플로우(AI Workflow Studio 구상)는 **별개 기능이 아니다.** 전략 루틴과 검증 루틴을 사용자가 원하는 대로 엮는 **범용 파이프**다.

- **대조 파이프**: `[매체 MCP] → [Normalizer] → [BO/RC 결과와 대조] → [리포트/알림]`
  - AI Workflow Studio 구상의 활용 시나리오 3번("예측 솔루션 입력 자동화")에 대조 노드 하나만 더 얹으면 검증 루틴이 닫힌다.
- **성과 모니터링 파이프**: `[스케줄] → [매체 MCP] → [Normalizer] → [집계] → [알림]`
  - 4-3 상시 모니터링이 이 위에서 돈다.

즉 워크플로우는 Performance Tracker의 **실행 엔진**이자, 사용자가 자기 방식대로 루틴을 조립하는 **캔버스**다. 매체 MCP는 이 파이프의 **입력구**(읽기 전용 실측 수집)로 들어온다.

## 6. MCP 연결·SpinX 설정 구조 — "인증 한 번, 어디서나 갖다 쓴다"

이 루프 전체가 매체 MCP 실측에 의존한다. 그래서 **연결을 매번·매 Slot마다 다시 하지 않게** 만드는 게 프로덕트 성패를 가른다. War Room의 "Zero-latency Flow" — 쓸 때마다 연동하는 수고는 전부 비용이다.

### 6-1. SpinX는 MCP를 쓰는 단일 주체다

MCP를 호출하는 주체는 **SpinX 하나**다. 솔루션에 붙은 SpinX(플로팅 챗)든 Workflow의 SpinX 노드든, **같은 SpinX 엔진 · 같은 연결**을 쓴다. 붙는 위치만 다를 뿐이다.

```
              [SpinX 엔진 + MCP 연결]   ← 설정은 여기 한 곳
                     │
          ┌──────────┴───────────┐
          ▼                      ▼
   솔루션에 붙은 SpinX        Workflow의 SpinX 노드
   (플로팅 챗 · 대화형)       (스케줄 파이프 · 무인)
   "이 광고주 실측 가져와      [매체 MCP]→[대조]→
    예측이랑 비교해줘"          [SpinX 서사화]→[알림]
```

그래서 설정을 두 벌 만들지 않는다. **설정은 한 곳, 사용처는 여러 곳.** 이 절의 핵심 문장이다.

### 6-2. 두 종류의 "연결"을 구분한다

혼동하기 쉬운데, 층이 다른 두 설정이 있다. 이 구분이 이 절에서 PO가 못박아둘 지점이다.

| | ① 매체 MCP 연결 (광고주 인증) | ② MCP 서버 활성화 (SpinX 도구 승인) |
|---|---|---|
| 무엇 | "광고주 A의 Google Ads 계정에 접근할 권한" (토큰) | "SpinX가 Google Ads MCP 서버를 써도 되는가" (함수 심사) |
| 단위 | **광고주 단위** | **플랫폼(App) 단위** |
| 관리자 | 그 광고주 권한을 가진 **사용자** | **SpinX 관리자(AX팀)** |
| 근거 | 이 문서 6-3 | 기존 `SpinX_MCP_사용_정책서` (등록→심사→승인→활성화) |

즉 "어떤 MCP를 SpinX 능력에 넣을지"(②, 관리자가 화이트리스트로 read-only 승인)와 "그 도구로 어느 광고주 데이터를 볼지"(①, 사용자가 광고주 인증)는 다른 층이다. 기존 정책서가 ②를 이미 설계했고, 이 문서는 ①을 얹는다. **둘이 맞물려 하나의 설정 화면을 이룬다.**

### 6-3. 매체 연결 = 광고주 단위 · 플랫폼 상주 · 공유형

인증을 매어둘 곳은 **Slot이 아니라 광고주(Advertiser)**다. 한 광고주 아래 Slot이 여러 개이므로, Slot에 매면 같은 광고주를 반복 인증하는 마찰이 생긴다.

```
플랫폼 (ReadySet)
│
├── 🔗 매체 연결 저장소 ── 광고주 단위로 토큰 격리
│     광고주 A → { Google Ads, Meta, ... }   ← 인증은 여기 한 번만
│     광고주 B → { Google Ads, TikTok, ... }
│         │ (광고주 컨텍스트로 참조)
│         ▼
├── Slot A-1 ─┐
├── Slot A-2 ─┤ ← 같은 광고주면 A의 연결을 공유 (Slot마다 재인증 없음)
├── Slot B-1 ─┘
│         ▼
└── 각 Slot 안: BO · RC · Performance Tracker · Workflow — 모두 그 광고주 연결을 갖다 씀
```

- **소유자 = 광고주 / 저장 위치 = 플랫폼 레벨 / 참조 = 광고주 컨텍스트.** GNB의 "광고주 선택" 드롭다운이 이미 그 컨텍스트를 제공한다. 매체 연결은 그 광고주에 매달린 자산이다.
- **공유형이다.** 그 광고주에 권한을 가진 담당자 A가 한 번 연결해두면, 팀원 B도 그 광고주의 어느 Slot·어느 작업에서든 바로 쓴다. 렙사는 한 광고주를 팀이 함께 다루므로 개인별 재인증은 불필요한 반복이다.
- **데이터 격리는 유지.** 플랫폼에 "저장"하되 아무 광고주나 공유하는 게 아니다. 토큰은 광고주별로 분리 보관되고, 광고주 A 작업 중엔 A 토큰만 쓰인다. (Workflow 구상 3.5의 "폴더=광고주 단위 토큰 격리"를 광고주 레벨로 정확히 올린 것.)

이 구조가 반복을 두 층에서 없앤다: **작업마다 재연동 없음 + Slot마다 재인증 없음.** 광고주당 매체별 인증은 딱 1회.

### 6-4. 이게 곧 "우리를 경유할 이유"

광고주가 Claude에 매체 MCP를 직접 붙이면 매체마다 자기가 인증해야 한다(팀 문서 별첨 D 방향1: "200개 중 개방은 소수, 나머지는 우리 경유"). ReadySet은 **광고주별로 여러 매체를 한 자리에서 연결·상주**시켜 그 마찰을 대신 없앤다. 마찰 제거 자체가 경쟁 우위의 한 조각이다.

### 6-5. PO가 정할 세부

- **연결 관리 UI 위치**: Slot이 아니라 **광고주 설정**(또는 플랫폼 설정)의 "매체 연결" 페이지. 광고주 선택 후 연결된 매체 목록.
- **연결 상태 가시성**: 각 Slot/작업에서 "이 광고주 — Google Ads·Meta 연결됨, TikTok 미연결"을 읽기 전용으로 노출. 끊겼으면 광고주 설정으로 유도.
- **토큰 만료·재인증**: OAuth 토큰은 만료된다. 만료되면 Workflow 자동 실행이 조용히 실패하므로, **만료 임박 알림 → 재인증 1회로 그 광고주의 모든 Slot 복구**. 이게 "쓸 때마다 마찰 없음"을 실제로 지키는 장치.
- **권한 범위**: read-only로 시작(실측 조회만, 집행 변경 권한 미수령). 팀 문서·MCP 정책서의 "읽기 전용 시작" 원칙 준수.

## 7. 가설검증연구소 — 루프가 한 바퀴 돈 뒤 열리는 방

가설검증연구소(Insight Archive 구상)는 **2027 확정 과제가 아니다.** Performance Tracker 루프의 산출물이 쌓여야 열린다.

- **흐름**: 대조에서 반복 검출된 패턴 → 검증된 인사이트로 승격 → SpinX RAG 소스 → 다음 예측 개선
  - (예) "이 업종은 프리퀀시 3 이상에서 효율이 꺾인다"가 여러 캠페인 대조에서 반복 확인 → 아카이브에 등재 → SpinX가 다음 광고주 예측 때 이 근거를 끌어옴.
- **왜 나중**: 대조 데이터가 없으면 검증할 재료가 없다. 팀 문서가 보정학습을 "2028년 이후, A2가 1년 돌아야 가능"으로 둔 것과 같은 논리.
- **이 문서에서의 처리**: 상세 설계하지 않는다. **"루프의 산출물이 흘러가는 종착지"**로 방향만 박아둔다. 어렵다는 것도 정직하게 남긴다 — 지금 무리하게 데이터 모델을 확정하지 않는다.

## 8. 매체 MCP 스펙 현황 (2026 조사)

Performance Tracker의 입력구가 될 매체 MCP가 실제로 어떤 상태인지 조사한 결과다. 우리 설계(읽기 전용 시작, 광고주 단위 인증)와 시장 현실이 얼마나 맞는지 확인하는 게 목적이다.

| 매체 | 공식 MCP | 권한 | 인증 | 비고 |
|---|---|---|---|---|
| **Google Ads** | O (2025.10 오픈소스화) | **읽기 전용** (현재 릴리스) | OAuth · 사용자 신원 위임 | "진단·분석용"으로 공식 포지셔닝. 쓰기는 별도 REST 필요 |
| **Meta** | O (2026.4.29 · Ads AI Connectors) | 읽기+쓰기 | Meta Business OAuth (개발자 앱 등록 불필요) | MCP+CLI 두 인터페이스, 동일 29개 tool(리포팅·캠페인관리·카탈로그·진단·데이터셋) |
| **TikTok** | O (2026.5.13 · Agentic Hub) | 읽기+쓰기 | TikTok Business 앱 | 캠페인관리·리포팅·오디언스·크리에이티브 |
| **Kakao Moment** | **X (공식 없음)** | — | — | Moment API는 존재. MCP는 서드파티/자체 래퍼만 |
| **Naver GFA** | **X (공식 없음)** | — | — | SearchAd는 서드파티 MCP(packative) 존재. GFA는 부재 |

> 확인 기준: 2026년 조사. Google/Meta/TikTok은 공식 서버 확인. 국내 매체는 공식 광고 MCP 부재 확인. 각 매체 tool 개수·권한 세부는 배포 전 재확인 대상.

### 이 조사가 우리 설계에 주는 함의

1. **"읽기 전용 시작"은 우리만의 조심성이 아니라 Google의 공식 안전 모델과 같다.** Google Ads MCP는 릴리스 자체를 "읽기 전용 · 진단/분석용"으로 못박았다. Performance Tracker는 실측 **조회**만 하므로 Google MCP를 그대로 쓸 수 있다. Meta/TikTok은 쓰기까지 열려 있지만 **우리는 읽기 스코프만 받는다.** (시장 논의도 "계정을 안 넘기고 분석만 얻는 법"으로 옮겨가는 중 — 우리 포지션과 일치)

2. **국내 매체(Kakao/Naver)는 공식 MCP가 없다 → 자체 래퍼가 필수이자 기회.** 국내 매체 실측을 대조 루프에 넣으려면 렙사가 보유한 API 매핑 자산(`kakao_api_mapping.json`, `naver_gfa_api_mapping.json`)으로 **자체 MCP(Workflow 구상 3.3)**를 만들어야 한다. 글로벌 경쟁사(및 광고주가 직접 붙이는 Claude)는 국내 매체를 커버 못 하므로, 이게 ReadySet의 국내 통합 강점이 된다.

3. **수집 최소 범위 로드맵**: 공식 MCP 있는 **Google → Meta → TikTok** 먼저, 그다음 **자체 래퍼로 Kakao/Naver**. 앞의 셋은 붙이면 되고, 뒤의 둘은 우리가 만들어야 하니 난이도·가치 순서가 자연스럽다.

## 9. 이게 왜 지금 맞는 방향인가 (외부 근거)

- 매체 공식 MCP는 2026년에 상향평준화됐다. Google(4/28)·Meta(4/29)·TikTok(5/13)이 3개월 안에 각자 공식 MCP 서버를 냈고, 업계는 "ads MCP는 이제 기본 사양"이라 부른다. → **MCP로 성과를 가져오는 것 자체는 차별점이 아니다.**
- MCP가 여는 건 **광고주 자기 데이터**뿐이다. 자기 업종 평균·경쟁사 대비 위치·매체 간 상대 효율은 **여러 광고주 이력을 가진 쪽만** 만든다.
- 그래서 ReadySet이 파는 한 문장: **"매체 MCP = 자기 데이터만 / ReadySet = 자기 데이터 + 시장 좌표 + 예측과의 대조."**
  - Performance Tracker는 이 "대조" 조각을 담당하는 프로덕트다.

> 외부 근거는 팀 문서 별첨 D와 같은 결론이다. 차이는 위치다 — 팀 문서는 이걸 "시장 입장 정리(별첨)"로 뒀고, 이 문서는 **프로덕트의 메인 무기(본문)**로 둔다.
