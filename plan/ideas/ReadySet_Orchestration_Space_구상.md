# ReadySet 오케스트레이션 공간 구상 (통합)

> 상태: **구상 중 (ideas)**. 확정 스펙 아님. **모든 네이밍은 가칭/미확정**이다.
> (이전에 흩어져 있던 `ReadySet_Crew_구상` · `Insight_Archive_구상` · `AI_Workflow_Studio_정책서`를 이 문서 하나로 합쳐 관리한다.
> "Crew" 포함 어떤 이름도 확정된 바 없다. 이름은 10장에서 따로 다룬다.)

---

## 0. 이 문서가 답하려는 질문

지금 ReadySet에는 **4개 솔루션이 직렬(serial)로** 놓여 있다 (DataShot → BudgetOpt 2.0 → Reach Caster, + Ad Curator). 하나를 끝내야 다음으로 맥락을 넘기는 선형 흐름이다.

여기서 생긴 고민은 전부 **한 뿌리**다.

1. 이 4개 솔루션 **+ 다른 에이전트 + MCP**를 **동시에(병렬로) 활용**할 수 있는, 솔루션에 종속되지 않는 **독립 IA**가 필요하다.
2. 그런데 이건 한 번에 못 만든다. **점진적으로 디벨롭**해야 한다.
3. 1차 가치: **데싸(데이터 사이언티스트)가 만든 데이터 분석 리포트를 어떻게 선제적으로 적용·발행**할 것인가.
4. 그 다음: 그 발행을 **어떻게 에이전트화**할 것인가.
5. 그 끝: **에이전트 플로우(여러 주체를 엮어 미션 수행)**를 어떻게 만들 것인가.
6. 가로지르는 과제: 사용자의 **MCP 관리 거버넌스**를 어떻게 수립할 것인가.

→ 이 여섯이 **하나의 공간 위에서 단계적으로 자라는** 그림을 이 문서가 그린다.

## 1. 한 줄 정의 (What)

> 특정 Slot(광고주·캠페인)에 **종속되지 않는 독립 공간**. 여기서 사용자는 ReadySet의 4개 솔루션, 외부/자체 에이전트, MCP 연결을 **한자리에서 동시에 불러 쓴다.** 이 공간은 "직렬 솔루션의 다음 단계"가 아니라, **솔루션들을 재료로 부리는 상위 레이어**다.

핵심 전환: **직렬(serial) → 오케스트레이션(orchestration).**
기존이 "도구를 순서대로 통과"라면, 이 공간은 "도구·에이전트·데이터를 **동시에 손에 쥐고 지휘**"한다. War Room DNA에서 지휘관이 참모진·상황판·무기를 동시에 다루는 그림.

- **왜 독립 IA인가**: 특정 솔루션 내부 탭에 넣으면 그 솔루션에 종속된다. 4개를 **가로지르고**, 그 밖의 에이전트·MCP까지 품으려면 솔루션과 **나란히 서는** 진입점이어야 한다.
- **왜 한 공간인가**: 데이터 리포트(지식) · 에이전트(실행 주체) · MCP(연결) · 워크플로우(엮기)는 따로 노는 기능이 아니라, **같은 공간의 성장 단계**다. 문서를 쪼개면 또 흩어진다. 그래서 하나로 묶는다.

### 1.1 이 공간의 상위 목적 — 예측과 실측의 결합 (2027 방향과의 접합)

이 독립 공간이 왜 필요한가는 `2027_ReadySet_Product_Direction_구상.md`의 큰 그림에서 나온다.

- **현재의 ReadySet** = 예측 + 기존 데이터 분석 추출 관점. (캠페인 시작 전 "이렇게 하면 이럴 것이다")
- **내년의 ReadySet** = **예측과 실측의 결합.** 집행 실측을 받아 예측과 대조하고, 그 대조가 다음 예측을 정교하게 만드는 닫힌 루프.

이 공간은 그 결합이 물리적으로 일어나는 무대다. 두 종류의 데이터가 여기서 만난다.

| 데이터 | 어디서 가져오나 | 성격 |
|---|---|---|
| **실측 데이터** | **매체 MCP** (Google/Meta/TikTok 공식, Kakao/Naver 자체 래퍼) | 집행 성과 조회 (read-only) |
| **예측 데이터** | **내부 자체 에이전트 / 자체 MCP** (BO·RC 등 솔루션 예측을 노출하는 주체) | 모델이 낸 예측 |

- 즉 이 공간에서 "솔루션 + 에이전트 + MCP를 동시에 부린다"의 실체 = **예측(내부 에이전트/MCP)과 실측(매체 MCP)을 한자리에서 대조**하는 것이다.
- 매체 MCP는 이 공간의 **실측 입력구**, 내부 예측 에이전트/MCP는 **예측 입력구**. 둘을 맞대는 게 렙사의 해자다 — 개별 광고주도, 범용 AI도 여러 광고주의 실측을 못 모은다.

> 상세한 예측↔실측 루프, Performance Tracker 레이어, 매체 MCP 스펙·인증 구조는 `2027_ReadySet_Product_Direction_구상.md`에 있다. 이 문서는 그 루프가 **어떤 공간 위에서, 어떤 순서로 자라는가**를 다룬다.

## 2. 점진 디벨롭 로드맵 (핵심 — 확정)

> 원칙: **각 단계가 그 단계만으로도 혼자 쓸 가치가 있어야** 다음 단계까지 사람이 남는다.
> 그리고 **각 단계의 산출물이 다음 단계의 재료**가 된다. 순서를 바꾸면 뒷단계가 성립하지 않는다.
> (아래는 PO 인터뷰로 확정된 로드맵. 기존 "리포트발행→에이전트화→플로우"를 재정의했다.)

### 핵심 구조 — 3레이어(양성) + 1종착(공급) + 2가로축

> 전략 프레임: **단계 1~3은 Ground 앱 안에서 해자(데이터·방법론·실측 노하우)를 "기르고", 단계 4는 그 해자를 MCP로 "공급"한다.** 안으로 축적 → 밖으로 유통. 순서가 뒤집히면 팔 재고가 없다.

```
레이어 1  지식 베이스 (DB화)         ← 데싸 분석 + 매체 소식. SpinX·에이전트의 참조물(RAG)
레이어 2  에이전트 플로우 + Skills    ← AdCurator→BudgetOpt 2.0→Reach Caster 제안셋 생성   ┐
            └ 레이어 1에서 맥락 맞는 분석을 자동으로 끌어와 설명력 보강                    │ Ground 앱에서
레이어 3  매체 MCP 실측 결합          ← "내 시나리오 vs 실제 집행결과 비교"                  │ 해자를 기른다
──────────────────────────────────────────────────────────────────                        ┘
종착 4   MCP 공급 (능력 노출)         ← 기른 해자(솔루션·지식·Skills)를 고객 LLM에 공급 ★전략 종착지
──────────────────────────────────────────────────────────────────
가로축 A  Skills                      ← 플로우/산출물 생성의 "방법"을 패키징해 재사용 (레이어 2와 한 몸)
가로축 B  MCP 거버넌스                ← 토큰 격리·권한 (레이어 3 전에 수립)
```

> **단계 4의 전략적 의미** (상세는 `2027_ReadySet_Product_Direction_구상.md`로 엮을 예정):
> - AI 시대 렙사가 UI로 범용 LLM과 경쟁하면 진다. 대신 범용 LLM이 못 가진 것(여러 광고주의 실 집행 데이터, 국내 매체 통합, 데싸의 검증된 방법론)을 **공급원으로 판다.**
> - Skills·MCP는 본질적으로 "내 LLM에 붙여 쓰는" 표준이다. 즉 Skills를 만든다는 것 자체가 단계 4(공급)를 향한 포석이다.
> - 단, **단계 4는 1~3 뒤에 온다.** 공급할 해자(지식·Skills·실측 노하우)가 Ground 앱에서 먼저 쌓여야 공급이 성립한다. Ground = 해자를 기르는 밭, MCP 공급 = 그 수확을 파는 유통.

### 단계 0 — 공간의 껍데기 (독립 진입점)
- GNB에 SlotBoard와 **나란히 서는 독립 메뉴** 하나를 연다. (가칭 **Ground** — 10장)
- 솔루션(ReachCaster/BudgetOpt/DataShot)과 병렬이 아니라 **SlotBoard와 병렬**이다. 솔루션은 Slot 하위, Ground는 Slot 비종속.
- 빈 무대가 아니라 **단계 1의 지식이 바로 들어차는 집**. 단계 1과 함께 연다.

### 단계 1 — 레이어 1: 지식 베이스 DB화 (⭐ 먼저, 뒷단계의 재료)
- **두 종류의 지식을 아카이빙하고, 발행형(저널)과 동시에 반드시 DB화**한다. DB화가 본질이고 저널은 표면이다.
  - **데싸 광고데이터 분석 결과** — 분석 개요 / 가설·결과 / 연계 솔루션 등 구조화 필드.
  - **매체 소식** — 광고 관련 모든 소식을 한자리에서 찾도록 아카이빙. 역시 DB화.
- **핵심 목적: 둘 다 SpinX의 참조물(RAG 소스)이자, 단계 2 플로우의 "설명력 보강" 재료.** "읽으라고" 쌓는 게 아니라 "에이전트가 꺼내 쓰라고" 쌓는다.
- ⚠️ **맥락 매칭 키(태그: 업종·기간·매체·KPI 등)를 생산 때부터 스키마에 심는다.** 단계 2에서 "연휴·IT 업종 분석을 자동으로 끌어오는" 매칭이 이 키에 의존한다. 여기서 안 심으면 뒤에서 못 만든다.

### 단계 2 — 레이어 2: 에이전트 플로우 + Skills (한 몸)
- **플로우**: 자연어 요청("2030 타겟 하이트진로 1억 제안셋 만들어줘")을 받아 `AdCurator(상품 리스트) → BudgetOpt 2.0(예산 배분) → Reach Caster(도달)`를 엮어 최종 제안셋을 산출.
- **설명력 보강**: 요청의 기간·업종을 보고, 단계 1 지식 DB에서 맥락 맞는 분석(예: 연휴 관련 + IT 업종)을 자동으로 끌어와 산출물에 붙인다. ← 레이어 1이 레이어 2의 재료가 되는 연결고리.
- **Skills (가로축 A, 여기서 같이 간다)**: 플로우가 산출물을 만들 때 매번 생프롬프팅하지 않도록, **작업 수행 "방법"을 패키징**한다. (Claude Agent Skills 모델 → 5.5장) Skills 없는 플로우는 반쪽이므로 단계 2에서 함께 만든다.

### 단계 3 — 레이어 3: 매체 MCP 실측 결합
- 광고주별 **매체 MCP**를 연동 → "내가 뽑아둔 시나리오 vs 실제 집행 결과를 비교해줘" 같은 사후 플로우.
- = 예측(우리 솔루션) ↔ 실측(매체 MCP)의 대조. 2027 구상의 닫힌 루프가 여기서 돈다.
- ⚠️ 가장 무겁다. 매체 MCP 인증·실행 엔진. 단계 1·2 검증 후 착수.

### 가로축 B — MCP 거버넌스
- 단계 1에선 거의 안 쓰이지만, 단계 3에서 외부 연결이 늘기 전에 **먼저 수립**돼야 토큰·권한 폭발을 막는다. (→ 6장)

```
단계0 껍데기 ─ 단계1 지식 DB화 ─ 단계2 에이전트 플로우 + Skills ─ 단계3 매체 MCP 실측 결합
                 (뒷단계 재료)        (플로우·Skills 한 몸)            (예측↔실측 루프)
   └──────── 가로축 A: Skills(단계2~) ────────┘
   └──────── 가로축 B: MCP 거버넌스 (단계3 전 수립) ────────┘
```

### 2.1 출시 전략 — 기술 순서와 출시 순서는 다르다
- **기술 의존 순서**는 1→2→3→4다. 지식 DB가 플로우의 재료이기 때문이다.
- **출시(사용자 첫 공개) 순서**는 별개다. 지식 DB 단독으로 열면 분석글과 매체 소식만 있는 게시판으로 읽혀 첫인상이 나쁘다. 지식은 재료이고, 사용자가 "오?" 하는 지점은 해주는 것(플로우 산출물)이다.
- **방향: 단계 1은 단독 데뷔하지 않는다.** 단계 1+2를 묶어 재료와 요리가 함께 있는 상태로 첫 공개한다. 단계 1은 단계 2의 받침대로 포지셔닝한다.
- 보조 안: 단계 1에 SpinX 능동 브리핑("오늘 당신 업종에 영향 줄 매체 변경 2건")을 얹어 읽는 게시판이 아니라 말 거는 공간으로 만든다.
- 일정 맥락: **AdCurator가 2027년 1Q에 출시 예정**이다. 이로써 플로우의 세 노드(AdCurator → BO → RC)가 1Q에 갖춰진다. 다만 AdCurator 출시와 Ground 단계 1·2를 한 분기에 몰면 과부하이므로, "1Q 공개"가 비전·기획서 공개인지 실제품인지 정의가 필요하다. (9장 오픈 퀘스천)

## 3. 단계 1 — 데싸 리포트 발행 (가장 먼저 만드는 것)

### 3.1 정체
- 마케터가 **감으로 결정하던 것(가설)**을 데싸가 **데이터로 검증**하고, 그 결과를 쌓아 발행·아카이브하는 콘텐츠 허브.
- "뉴스레터"는 **발송 방식**일 뿐이다. 원본은 이 아카이브에 쌓이고, 뉴스레터는 거기서 **골라 묶어 내보내는 배포 액션**이다. (원본 ≠ 배포 채널)
- 성격: 콘텐츠 + 지식 베이스. 특정 솔루션에 종속되지 않는 **크로스 인사이트**.

### 3.2 리포트 1건의 구조 (3층 + 서명)
데싸가 주는 가설 예시(5.3)에서 뽑은 공통 패턴을 포맷으로 고정한다.

| 층 | 내용 | 비고 |
|---|---|---|
| ① 제목 (마케터 언어) | 훅. "돈을 더 썼는데 왜 순도달은 그대로지?" | 쉬운 말로 바꾸지 않고, 재밌는 훅 + 어려운 그대로 |
| ② 가설 원문 (검증 언어) | 데싸가 쓴 검증 가능한 명제 | |
| ③ 검증 결과 | 데이터 출처 + 방법론 + 결론 + 신뢰도 | "있어 보임 = 근거" |
| ④ 실행 제안 (그래서 뭐?) | 렙사/마케터가 취할 액션 한 줄 | 숫자만 던지지 않는다 |
| ⑤ 저자 서명 (크레딧) | 누가(어떤 전문성으로) 검증했나 + 방법론명(Meridian 등) | "창작물에 서명" = 단계 2 에이전트화의 씨앗 |
| ⑥ 적용 맥락 태그 | 업종 / 매체 / KPI / 실측·예측 상황 등 | **큐레이터 에이전트(4.2)가 "이번 케이스에 적합한가"를 판정하는 키.** 생산 때부터 심어둔다 |

> ⑤ 서명이 핵심이다. 단계 1에선 사람(데싸) 서명, 단계 2에선 에이전트 서명으로 **자연스럽게 확장**된다. 즉 "에이전트 저널"의 정체는 자동화가 아니라 **저자에 서명을 붙이는 구조**다.
> ⑥ 태그는 단계 2 **큐레이터 에이전트의 재료**다. 리포트를 쌓을 때부터 맥락 태그를 붙여둬야, 나중에 "이 케이스에 맞는 리포트"를 골라낼 수 있다. 단계 1 데이터 모델 설계 시 ⑥을 반드시 포함한다.

### 3.3 인접 축 — 브리핑 데스크 (매체 공지 큐레이션)
- 매체(구글·메타·네이버·카카오 등) 공지사항을 한자리에 모아 보는 큐레이션.
- 리포트 아카이브와 성격 구분:
  - 리포트 = **가설→검증→결론** (능동적 발견, 우리가 만든 지식)
  - 브리핑 = **매체 공지 수집·정리** (수동적 큐레이션, 외부 원문 기반)
- 같은 공간에 두는 이유: 둘 다 크로스 콘텐츠이고, "플랫폼이 살아있다(최신 정보가 계속 갱신)"는 상황판 감각을 함께 만든다.
- 확장: 공지 중 예측·배분에 영향 주는 변경을 SpinX가 감지해 "이 캠페인에 영향 있어요"로 잇기. → 단계 3 플로우의 트리거 후보.

### 3.4 메인 연계
- 최신 리포트를 메인(SlotBoard) 상단 **카드/티커**로 노출 → "지금도 새 인사이트가 쌓인다"는 감각.
- 쌓인 리포트는 **SpinX RAG 단일 소스(single source)**로 인덱싱. "내 캠페인을 나보다 잘 아는 파트너"의 근거.

### 3.5 지식 베이스의 본질 — 발행형은 표면, DB화가 본체 (PO 확정)
- 지식은 두 종류이고, **둘 다 저널(읽는 발행물)로 보이되 반드시 구조화 DB로 보유**한다.
  - **데싸 분석 결과**: 분석 개요 / 가설·결과 / 연계 솔루션 등 구조화 필드.
  - **매체 소식**: 프로모션·신상품 등 광고 관련 소식 전부. 광고와 관련된 건 여기서 다 찾는다.
- **공통 지식 스키마**를 쓴다. 두 타입은 필드 일부만 다르고, **맥락 태그와 가시성 플래그 구조는 공유**한다.
- 목적: 둘 다 SpinX의 참조물(RAG)이자 단계 2 플로우의 설명력 보강 재료.
- **플랫폼에는 분석 결과(구조화 데이터)만 가져가고, 캐릭터·브랜딩은 가져가지 않는다.** 데싸의 뉴스레터 파일럿(위니 캐릭터, 이메일 채널)은 플랫폼과 무관한 배포 스킨으로 그대로 둔다. 같은 스키마 데이터에서 플랫폼 화면과 메일 본문을 모두 만드는 구조를 지향한다. 메일의 솔루션 연결 배너는 플랫폼에서 "연계 솔루션" 필드로 대응한다.
- **플랫폼에서 리포트를 해석·안내하는 주체는 SpinX다.** 위니 같은 별도 안내자 페르소나를 두지 않는다. 역할을 둘로 나눈다.
  - **데싸의 시사점**: 리포트에 고정된 저자 서명 콘텐츠. 누가 검증했는지가 남는다.
  - **SpinX의 해석**: 지금 보는 캠페인 맥락에 맞춰 동적으로 생성. 리포트 근거를 인용하고, 데싸 콘텐츠와 구분해 표시한다. 데싸의 결론을 대체하지 않는다.
- **매체 정보는 실시간 조회가 아니라 Ground가 구조화해 보유한다.** 사내 기간계에 있지만 양식이 제각각이라, 실시간 조회로는 태그가 없어 RAG 매칭이 안 된다. 정제 과정 자체가 Ground의 가치다. 보유하면 브리핑 피드 노출과 SpinX 참조를 같은 DB로 처리한다.

### 3.6 수집·정규화 레이어 (ingestion)
상위 개념으로 둔다. 비정형 원본이 공통 스키마 DB에 들어가기 전에 거치는 공통 관문이다.

```
비정형 원본 → [수집·정규화 레이어: 스키마 정리 + 맥락 태그 + 가시성 플래그] → 공통 지식 스키마 DB → SpinX RAG / 브리핑 피드 / 플로우 보강
```

| 경로 | 원본 | 정규화 방식 |
|---|---|---|
| 매체 경로 | 사내 기간계의 기계 데이터 (양식 제각각) | **Normalizer** (매핑 JSON, 자동) |
| 분석 경로 | 데싸가 쓴 글·문서 | **구조화 입력 / 태깅** (사람, 폼) |

- 공통점은 저장 구조(공통 스키마, 맥락 태그, 가시성 플래그)다. 정규화 구현 방식은 콘텐츠별로 다르다.
- "Normalizer"는 매체 경로 전용 명칭이다. 분석 경로에 같은 이름을 붙이지 않는다.
- 매체 경로 파이프라인(수집 → Normalizer → 태깅 → 적재)은 화면이 없는 백엔드 영역이다. 기획서에서는 아키텍처 노트로 명시하고 개발 핸드오프 대상으로 둔다.

### 3.7 접근제어 — 두 축 플래그, 검색 전 필터 (PO 확정)
지식 레코드, 그리고 향후 Ground의 모든 콘텐츠 자산(플로우 산출물·Skills 포함)에 공통으로 다는 속성이다.

| 필드 | 의미 | 예 |
|---|---|---|
| `slotScope` | 특정 Slot(광고주) 소속인지, 전역(크로스)인지 | 매체 프로모션 = 전역 |
| `audienceLevel` | 누가 볼 수 있나 (신분 기준). 초기값은 `public` / `internal(임직원)` 2단계, 값 추가로 확장 | 매체 프로모션 = `internal` |

- 기존 Slot 가시성(`Internal / Private / Shared`)은 "어느 광고주 것이냐"의 축이다. `audienceLevel`은 "너는 임직원이냐"의 축이다. **축이 달라서 하나로 합치지 않는다.** 필터링 메커니즘만 재사용한다.
- **SpinX는 어느 솔루션에 붙어 있든 동일하게 두 축을 AND로 필터한다.**
- **필터는 반드시 검색 전(pre-filter)에 건다.** 권한 없는 지식은 후보에서 아예 제외한다. 검색 후 답변에서 가리는 방식은 LLM이 내용을 읽고 흘릴 수 있어 금지한다.
- 지식을 한 곳에 저장하고 검색 시점에 권한으로 거른다. 인덱스를 임직원용·외부용으로 나누지 않는다.
- 플로우 산출물·Skills의 가시성 등급은 아직 미설계다. 같은 플래그를 얹을 자리만 열어둔다.

## 4. 단계 2 — 발행의 에이전트화

> 단계 1에서 **사람이 하던 일의 어디를 에이전트가 대신할 수 있나**를 하나씩 뗀다.

에이전트화에는 두 방향이 있다. **생산**(리포트를 쓰는 쪽)과 **활용**(쌓인 리포트를 꺼내 쓰는 쪽). 그런데 렙사에게 진짜 킬러는 **활용 쪽**이다 (4.2).

### 4.1 생산 방향 — 리포트를 거드는 에이전트
- 후보 작업: 매체 공지 수집, 데이터 전처리/집계, 가설 초안 뽑기, 리포트 문장 생성.
- **단일 에이전트** 수준. 플로우(여럿 엮기)는 아직 아니다.
- 서명(3.2-⑤)이 사람 → 에이전트로 확장. 독자는 "이 검증을 수행한 주체"를 계속 본다.

### 4.2 활용 방향 — 리포트 큐레이터 에이전트 (⭐ 렙사 킬러)

> 핵심 통찰: 리포트를 쌓기만 하면 **"수많은 리포트" 더미**가 된다. 정작 사용자가 지금 하는 실측/예측 리포팅에 **어떤 가설 검증이 적합한지**는 모른다. 그걸 아는 에이전트를 하나 둔다.

- **정체**: 아카이브에 쌓인 가설검증 리포트를 **전부 알고 있는 담당 에이전트.** 사용자가 지금 다루는 케이스(업종·매체·KPI·실측/예측 상황)를 보고, **"이 케이스엔 이 가설 검증이 들어맞아요"**를 골라 설명한다.
- **왜 렙사에게 킬러인가**: 우리 회사는 **렙사**다. 실 집행 데이터를 **얼마나 잘 활용하느냐**가 관건이다. 검증된 인사이트가 아무리 많아도, 지금 이 캠페인에 맞는 걸 **꺼내 적용**하지 못하면 죽은 아카이브다. 큐레이터 에이전트가 "쌓인 지식"을 "지금 쓰는 지식"으로 바꾼다.
- **동작 상상**:
  - (사용자) "A업종 캠페인 실측이 예측보다 순도달이 안 나와요."
  - (큐레이터 에이전트) "예시 3 '동종 매체 잠식' 리포트가 이 케이스에 맞습니다. 타겟·시간대가 겹치는 두 매체는 합산 노출만 늘고 순도달이 안 늘어요. 지금 A매체와 B매체가 그 관계로 보입니다." + 해당 리포트로 바로 연결.
- **기술 성격**: 이게 Insight Archive 구상의 **SpinX RAG 소스**가 실제로 작동하는 모습이다. 아카이브(단계 1) = 지식 소스, 큐레이터 에이전트(단계 2) = 그 소스를 지금 케이스에 매칭·설명하는 RAG 주체.
- **단계 접합**: 단계 1이 **지식을 쌓고**, 단계 2 큐레이터가 **꺼내 적용**하고, 단계 3 플로우가 **대조 파이프에 자동으로 끼워** 넣는다. ("실측 수집 → 예측 대조 → 적합 리포트 큐레이션 → 서사화" 한 흐름)

### 4.3 열린 질문 (아래 9장)
- (생산) 에이전트 초안의 **검수 주체**(데싸 승인 게이트?), 자동/수동 혼합 비율, 신뢰도 표기.
- (활용) 큐레이터의 **적합도 판정 근거** — 업종·매체·KPI 태그 매칭인가, 의미 임베딩인가, 혼합인가.
- (활용) 큐레이터가 **틀린 리포트를 들이댈 때**의 안전장치 — 신뢰도/근거를 같이 보여주고, 사용자가 판단하게.

## 5. 단계 3 — 에이전트 플로우 (여럿 엮기)

> 기존 `AI_Workflow_Studio_정책서 v0.1`의 내용을 여기로 흡수한다. (노드·연결·실행·MCP 구조)

### 5.1 정의
- 사용자가 **노드를 캔버스에 배치·연결**해, 데이터 수집·가공·분석·리포팅을 자동화하는 흐름을 **시각적으로 설계·실행**.
- 기존 4개 솔루션이 "정해진 로직 실행"이라면, 여기선 **흐름 자체를 조립**한다.
- 재료: ReadySet 4개 솔루션 + 외부/자체 에이전트 + MCP 노드.

### 5.2 구조 요약 (상세는 흡수 원문 참조)
```
공간
└── 워크플로우 (최소 실행 단위)
    └── 노드(Node) ×N + 연결(Edge) ×N
        └── MCP 커넥션 (외부 서비스 연결)
```
- 노드 카테고리: 트리거 / 데이터소스 / 변환(Normalizer) / AI(LLM) / 로직 / 출력.
- 제약: 순환 금지(DAG), 트리거 최소 1개, 연결 시 입출력 스키마 정합성 검증.
- 실행(Run): 위상 정렬 → 순차/병렬 실행 → Run ID로 불변 이력 보관.
- 구성(Update)은 허용하되 **개별 실행 이력(Run)은 불변**.

### 5.3 단계 1·2와의 접합
- 단계 3의 **출력(Output) 노드 목적지 = 단계 1의 리포트 아카이브.**
- 즉 "매체 공지 수집 → 영향 분석 → 리포트 초안 생성 → 아카이브 적재"가 한 플로우로 돈다.
- 이렇게 해야 단계 1(사람이 쓰던 저널)이 단계 3에선 **에이전트가 채우는 공장**으로 이어진다.
- **큐레이터 에이전트(4.2)도 플로우 노드가 된다**: `[매체 MCP 실측] → [Normalizer] → [예측 대조] → [적합 리포트 큐레이션] → [SpinX 서사화 → 알림]`. 단계 2에서 대화형으로 쓰던 큐레이터를, 단계 3에선 **대조 파이프에 무인으로 끼워** 넣는다. (2027 구상 5장 "대조 파이프"에 큐레이션 노드 하나 추가)

### 5.4 활용 시나리오 예시
| # | 시나리오 | 노드 구성 |
|---|---|---|
| 1 | 통합 성과 리포트 자동화 | [스케줄] → [Google/Meta/TikTok Ads] → [Normalizer] → [집계] → [Sheets/Slack] |
| 2 | 매체 데이터 기반 AI 요약 | [매체 MCP] → [Normalizer] → [LLM 요약] → [리포트 아카이브] |
| 3 | 예측 솔루션 입력 자동화 | [매체 실적 MCP] → [Normalizer] → [BudgetOpt 2.0 연계] |

### 5.3.1 디자인 메모 — 연결 그래프를 노드 디자인의 기준으로 (PO 코멘트)
- Ground 홈의 "리포트와 시나리오 연결" 그래프(`src/components/ground/GroundGraph.tsx`)를 Agent Flow 노드·엣지 디자인의 출발점으로 삼는다.
- 이어받을 요소: 무채색 노드 + 1px 엣지, 종류별 노드 형태(채움/외곽선/크기), 호버 시 이웃만 남기고 흐리게, "바로 해당" 엣지만 시그니처 그린, 클릭은 고정이고 이동은 사이드 패널 링크로, 사이드 패널에 연결 이유를 노출.

### 5.4.1 대표 시나리오 — "제안셋 생성" (PO 확정 예시)
> 이게 레이어 2 플로우의 1순위 모습이다.

- (요청) "2030 타겟, 하이트진로 광고 1억, 제안셋 하나 만들어줘." (자연어 트리거)
- (플로우) `[AdCurator: 상품 리스트] → [BudgetOpt 2.0: 예산 배분] → [Reach Caster: 도달] → [제안셋 조립]`
- (설명력 보강) 캠페인 기간 10/1~10/31 + 업종 IT를 키로, 단계 1 지식 DB에서 **연휴 관련 분석 중 IT 업종 건**을 자동으로 끌어와 산출물에 근거로 붙임.
- (단계 3 확장) 하이트진로 매체 MCP가 연동돼 있으면, 나중에 "이 시나리오 vs 실제 집행 결과 비교해줘"가 가능.

### 5.5 Skills (가로축 A) — 작업 "방법"의 재사용 패키지

> 정체: 플로우/에이전트가 결과물을 만들 때 **매번 긴 프롬프팅을 다시 하지 않도록**, 작업 수행 방법을 한 번 패키징해 재사용하는 단위. **Claude Agent Skills 모델을 그대로 차용**한다.

- **동작 원리 (Claude Skills와 동일)**:
  - Skill = 폴더 하나. 안에 `SKILL.md`(필수) + 참조 파일·스크립트·에셋(선택).
  - `SKILL.md` = YAML 메타(name + description) + 본문(수행 방법 지시문).
  - **점진 공개(progressive disclosure)**: 에이전트는 평소 메타만 들고 있다가, 상황이 맞으면 그제야 본문을 읽어 장착. 컨텍스트 절약 + 무한 확장.
  - 선택은 키워드 매칭이 아니라 description을 보고 에이전트가 "지금 이 스킬을 쓰겠다"고 판단하는 학습된 행동.
- **예시**: `skill: Reach Caster 결과 광고주 대상 설명 자료` — RC 결과를 광고주용 설명자료로 만드는 방법(강조할 수치·톤·순서)을 한 번 정의. 다음부턴 "이 스킬로 만들어줘" + "이번엔 기간만 강조" 정도만 얹으면 됨.
- **왜 플로우와 한 몸인가**: 플로우가 "무엇을 순서대로"라면 Skills는 "각 산출물을 어떤 방식으로 만드는가". Skills 없는 플로우는 매번 생프롬프팅 = 반쪽. 그래서 단계 2에서 같이 간다.

### 5.5.1 Skills ≠ 레이어 1 지식 (데이터 모델에서 분리할 것)
둘 다 "에이전트가 참조하는 것"이지만 성격이 다르다. **데이터 모델에서 섞지 않는다.**

| | 레이어 1 지식 (3장) | Skills (5.5) |
|---|---|---|
| 답하는 질문 | **무엇이 사실인가** (검증된 데이터 지식) | **어떻게 만드는가** (작업 수행 절차·톤·포맷) |
| 쓰임 | 플로우의 설명력 **보강 재료** | 산출물 **생성 방법** |
| 형태 | 구조화 DB 레코드 + 맥락 태그 | 폴더(`SKILL.md` + 에셋) |
| 참조 주체 | SpinX RAG / 플로우 | 플로우 / 에이전트 |

## 6. 가로지르는 축 — MCP 관리 거버넌스

> 단계 2·3에서 외부 연결이 늘기 전에 **먼저** 수립돼 있어야 한다. 늦게 손대면 토큰·권한이 폭발한다.

### 6.1 커넥션 유형
| 유형 | 정의 | 예시 |
|---|---|---|
| 공식 MCP | 외부 서비스 공식 제공 | Google Ads, Meta Ads, TikTok Ads, GA4 |
| 자체 MCP | ReadySet 자체 구축 | Normalizer(매핑 JSON), Kakao/Naver 래퍼 |

> 차별점: Kakao/Naver 등 국내 매체는 공식 MCP 부재 → 기 보유 매핑 자산(`google/kakao/naver_gfa/facebook_api_mapping.json`)으로 **자체 MCP 구축.** ReadySet만의 국내 매체 통합 강점.

### 6.2 거버넌스 원칙 (수립해야 할 뼈대)
- **토큰 격리**: 매체별 인증 토큰(OAuth 등)은 **폴더(광고주) 단위**로 분리 보관. (공통 데이터 격리 정책 준수)
- **권한 상속**: 커넥션/워크플로우 실행은 해당 폴더의 가시성·접근 권한을 상속.
- **등록/관리 권한**: 커넥션 등록·토큰 관리는 관리자/운영자. 외부 사용자(대행사/광고주) 권한 범위는 🚩미결.
- **사용 통제**: 노드에서 커넥션을 쓰는 권한과 등록하는 권한을 분리할지 🚩미결.
- **레이트리밋/비용**: 매체 API 호출량 + LLM 토큰 사용량 관리 정책 🚩미결.
- **감사(Audit)**: 누가 어떤 커넥션을 언제 등록/사용했나 추적 (단계 2·3에서 중요해짐).

### 6.3 거버넌스가 로드맵과 만나는 지점
- 단계 1: MCP 거의 미사용. (사람이 데이터 들고 옴)
- 단계 2: 단일 에이전트가 1~2개 공식 MCP 사용 → **등록/격리 정책 필수**.
- 단계 3: 다수 커넥션 동시 사용 → **레이트리밋·감사·비용 통제 필수**.

## 7. IA 스케치 (잠정, 이름 전부 가칭)

```
ReadySet
├── / (= /slotboard)  SlotBoard      ← Slot들이 사는 홈. 솔루션의 상위 컨테이너
│     └── /slot/:id → ReachCaster / DataShot / BudgetOpt 2.0 / Ad Curator (Slot 종속)
└── /ground  [독립 공간, SlotBoard와 병렬]  ← Slot 비종속. 솔루션+에이전트+MCP를 동시에 ★이 문서
    ├── /ground (히어로)              ← 묵직한 인트로 → 입장 [단계 0]
    ├── 지식 베이스 (DB)              ← 데싸 분석 + 매체 소식. SpinX 참조물 [단계 1 ⭐]
    │   ├── 분석 아카이브             ← 가설→검증→결론 + 맥락 태그
    │   └── 브리핑 데스크             ← 매체 소식 큐레이션
    ├── 에이전트 플로우               ← AdCurator→BO→RC 제안셋 + 지식 자동 보강 [단계 2]

    └── MCP 커넥션                    ← 실측 결합 + 거버넌스 [단계 3, 가로축 B]
```

## 8. 제품 태도와의 연결 (Why 강한가)

- "감으로 결정 → 데이터로 검증" = **수치 너머의 큐레이션 / 발견의 희열**.
- 검증에 방법론·근거를 붙임 = **"있어 보임 = 근거 + 크래프트맨십"**의 콘텐츠 버전.
- 리포트에 저자 서명 = **창작물에 대한 존중**. 단계 1(사람)→2(에이전트)로 자연스럽게 확장.
- 솔루션+에이전트+MCP를 한 무대에서 지휘 = **War Room 상황실** 그 자체.

- 상위 그릇은 **단계 1~3 + MCP를 다 품는 중립 그릇**이어야 한다.
