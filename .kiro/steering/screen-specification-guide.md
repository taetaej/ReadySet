# 화면 상세 명세서 작성 가이드

## 이 문서의 활용처 (반드시 고려)

화면 정의서는 개발 참조로 끝나지 않고 **두 가지 하류 산출물의 원천 데이터**가 된다. 작성 시 항상 이 두 목적을 염두에 둔다.

### 1. 제품 Docs (기능 설명)의 기반

- 정의서의 **기획 의도·동작 설명**이 사용자 대상 문서로 재가공된다
- 따라서 "왜 이 기능이 필요한가 / 사용자가 무엇을 할 수 있는가"가 **사용자 관점 언어**로도 읽히게 서술한다
- 내부 구현 용어(변수명 등)에만 의존하지 말고, 기능의 목적을 자연어로도 남긴다

### 2. AI 기반 테스트 케이스(TC) 생성의 베이스 데이터

- AI가 이 문서만 보고 TC를 만들 수 있어야 한다 → **모든 규칙은 검증 가능(testable)**해야 한다
- 각 규칙은 **입력(조건) → 기대 결과(에러 메시지/동작/버튼 상태)**가 1:1로 도출되게 쓴다
- 경계값(=, ≥, 최대 자릿수 등), 정상/에러 케이스, 상호배타 조건을 빠짐없이 → 그대로 TC 항목이 된다
- 에러 메시지는 **실제 노출 문구 그대로** 기재 (TC의 기대값이 됨)
- "예상 플로우" 시나리오는 TC의 시나리오 테스트로 직결되므로 정상/에러 흐름을 함께 제공

> 요약: **Docs를 위해 "의도"를, TC를 위해 "검증 가능한 규칙과 기대 결과"를** 모두 담는다.

## 핵심 원칙

### 원칙 1 — 기획 의도가 최우선

명세서의 목적은 **"이 화면이 왜 이렇게 동작해야 하는가"(기획 의도)**를 전달하는 것이다.
모든 규칙·제약·동작에는 **그렇게 정한 이유**가 드러나야 한다. 개발자가 "왜 이렇게?"라고 물을 여지를 남기지 않는다.

- 단순히 "검색은 부분 일치"라고만 쓰지 말고, 동작이 사용자 관점에서 어떤 결과를 주는지가 드러나게 쓴다
- 규칙은 "무엇을 막는가 / 무엇을 허용하는가"와 그 목적을 함께 서술한다

### 원칙 2 — 동작 수준(내용)은 구체적으로, 시각 수치는 코드에 위임

- **동작·내용 수준**(검색 매칭 방식, 입력 제한, 상태 전환 부수효과 등)은 **추측이 필요 없을 만큼 구체적으로** 명시한다
- **정확히 어떻게 보이나**(px, hsl 색상, grid 문법)는 **구현 코드와 디자인 시스템 토큰이 단일 진실 공급원(Single Source of Truth)**이다

> 프론트엔드 개발자는 이미 구현된 컴포넌트/디자인 토큰을 가져다 쓴다.
> 스타일 수치는 코드에 위임하되, **동작 규칙은 절대 생략하지 않는다.** 이 둘을 혼동하지 말 것.

### 남길 것 vs 뺄 것

| 남긴다 (기능·의도) | 뺀다 (구현 디테일) |
|---|---|
| 좌우 2단 + 우측 sticky 요약 구조 | `grid-template-columns: 1fr 1px 420px`, `gap 48px` |
| 입력 최대 11자리(999억) 제한 | 입력 필드 `width: 260px` |
| 잠금은 아이콘 사용(이모지 X) | `Lock size={8}`, `hsl(var(--primary))` |
| 에러는 단일 destructive 스타일 | `fontSize: 11px`, `marginTop: 4~8px` |
| 최소 2개 상품 필요 | muted 배경 `hsl(var(--muted)/0.5)` |

**규칙**: 레이아웃의 의도·비율 개념은 남기고, 정확한 px/hsl/grid 문법은 "구현 코드 / 디자인 토큰 기준"으로 위임한다.

## 문서 구조 (권장 순서)

Budget Optimizer 시나리오 생성 정의서(`plan/spec/BudgetOptimizer_Scenario_Creation_Spec.md`)를 모범 사례로 참고한다.

1. **문서 정보 + 변경 이력** — 버전, 작성일, 대상 화면, 관련 정책서, 변경 이력 표
2. **화면 개요** — 기능 정의(+기획 의도), 문서 활용처(Docs/TC), 진입 경로(URL), 화면 구조
3. **레이아웃** — 구조 다이어그램(ASCII), 영역 구성 (수치 아닌 의도 중심), Breadcrumb
4. **단계/영역별 상세** — 입력 필드 표(필수/타입/제한/기본값), 세부 동작
5. **유효성 검증 규칙** — 아래 "유효성 규칙 작성법" 참조
6. **인터랙션 플로우** — 정상 플로우 + 주요 에러 시나리오
7. **공통 입력/인터랙션 규칙** — 검색·금액·텍스트·토글 등 공통 동작
8. **데이터 개념 및 용어 매핑** — 인터페이스 코드가 아닌 개념 + UI↔필드 매핑
9. **개선 제안 (이 화면 한정)** — 아래 "개선 제안 작성법" 참조
10. **참고 자료** — 관련 정책서, 구현 컴포넌트 파일 경로, 관련 스펙

## 유효성 규칙 작성법

규칙이 많아지면 번호가 소통 언어가 된다. 다음 원칙을 지킨다.

- **그룹핑**: 검증 대상별로 그룹(예: A 기본입력 / B 금액입력 / C 계층 / D 전역)으로 분류
- **순차 번호**: 그룹 내 연속 번호 부여(V1, V2, ...). 중간에 빈 번호(R2, R7 누락 등)를 만들지 않는다
- **요약 표 먼저**: `# / 그룹 / 규칙명 / 조건 / 에러 레벨` 요약 표를 상단에 배치
- **규칙별 상세**: 조건(의사코드) + 에러 메시지(실제 문구) + 표시 위치 + 검증 타이밍
- **엣지 케이스 명시**: 경계값(=, ≥), 상호 배타 조건, 중복 카운트 방지 등을 빠짐없이
- **종합 유효성 조건**: 다음 단계 진행 가능 조건을 코드 형태로 정리

> **TC 연계**: 각 규칙은 그대로 하나 이상의 테스트 케이스가 된다.
> `조건(입력) → 기대 결과(에러 메시지 원문 / 버튼 disabled 여부)`가 명확해야 AI가 TC를 자동 생성할 수 있다.
> 정상 통과 케이스와 위반 케이스를 모두 도출 가능하도록, 경계값을 양쪽(예: 합계 = 매체 금액 / ≠ 매체 금액)으로 서술한다.

## 인터랙션 세부 규칙 (추측 방지 — 내용 수준까지)

개발자가 추측하지 않도록 **동작의 내용 수준까지** 명시한다. 아래는 각 항목에서 반드시 답해야 할 질문과 실제 서술 예시다.

### 검색 필드

반드시 답할 것:
- **매칭 방식**: 부분 일치(substring) / 완전 일치 / 접두 일치 중 무엇인가?
- **대소문자**: 무시(case-insensitive)인가 구분인가?
- **공백 처리**: 트리밍하는가, 입력 그대로 비교하는가?
- **타이밍**: 실시간(onChange)인가 엔터/버튼 트리거인가? 디바운스가 있는가?
- **검색 대상**: 어떤 필드들을 검색하는가? (예: 매체명 + 상품명 동시)
- **결과 없을 때**: 항목을 숨기는가, "결과 없음"을 표시하는가?

> 예시 (Budget Optimizer 다이얼로그):
> "매체명 + 상품명을 동시에 **부분 일치(substring)**로 검색하며 **대소문자를 무시**한다. 공백 트리밍 없이 입력 그대로 비교하고, onChange 실시간 필터(디바운스 없음)로 동작한다. 매체명이 일치하면 해당 매체의 모든 상품을, 상품명이 일치하면 해당 상품만 노출하며, 결과 없는 매체는 리스트에서 숨긴다."

### 금액/숫자 입력

반드시 답할 것:
- 입력 타입(text vs number), 표시 포맷(천 단위 콤마 등)
- 파싱 규칙(콤마 제거 후 정수 변환, 비숫자 입력 처리)
- 자릿수/범위 제한(예: 최대 11자리 = 999억), 초과 시 차단 여부
- 단위 표시, 소수점 허용 여부, 보조 표기(예: 한글 금액 병기)

### 텍스트 입력

- maxLength 값, 초과 입력 처리(차단 vs 절삭), 글자 수 카운터 표시 여부

### 토글 / 삭제 / 상태 전환

- 상태 전환 시 **부수 효과**를 명시 (예: 잠금 해제 시 금액 0으로 초기화)
- 삭제 시 **연관 데이터 처리** (예: 매체 삭제 → 하위 상품 + 매체 잠금 상태 함께 제거)
- 라디오/모드 전환 시 초기화되는 값

### 선택 / 다이얼로그 상태

- 다이얼로그 재오픈 시 이전 상태 복원 여부
- 전체 선택이 필터 결과 기준인지 전체 기준인지
- 취소/오버레이 클릭 시 변경사항 처리(반영 vs 폐기)
- 확인 시 기존 항목의 부가 상태(예: 잠금 값) 보존 여부, 신규 항목의 기본값

## 스타일 서술 방식

정확한 값 대신 **의도와 토큰**으로 서술한다.

| 지양 | 지향 |
|---|---|
| `너비: 420px` | "우측 고정폭 패널, sticky로 상단 고정" |
| `fontSize: 11px; color: hsl(var(--destructive))` | "필드 하단 작은 텍스트, destructive 토큰 색상" |
| `borderRadius 8px; hsl(var(--muted)/0.5)` | "muted 배경 박스 (기존 컴포넌트 동일)" |
| `🔒 이모지` | "lucide-react `Lock` 아이콘" |

- 색상은 디자인 토큰명(`--destructive`, `--primary`, `--muted`)으로 지칭
- 다른 화면과 동일하면 "○○(참조 화면)과 동일"로 재사용 명시

## 데이터 구조 서술

- **타입 정의(인터페이스 코드 전문)는 스펙에 넣지 않는다** — 구현 코드가 단일 진실 공급원. 스펙엔 규칙·플로우 이해에 필요한 **개념과 용어 매핑**만 남긴다
- **구조적 특징**만 서술 (예: "계층을 flat 배열 + 별도 잠금 상태로 관리" 정도의 개념)
- **UI 용어 ↔ 데이터 필드 매핑**은 명시 (예: UI "잠금" = 필드 `isFixed`) — 유효성 규칙에서 필드명을 쓰는 경우 이해를 돕기 위함
- 정확한 타입/필드 목록이 필요하면 구현 파일 경로를 참조로 남긴다

## 개선 제안 작성법 (이 화면 한정)

향후 개선 항목은 **해당 화면 범위 안**의 것만 담는다.

- **범위 판단**: 이 화면에서 직접 조작·발생하는 개선인가? 목록/결과/솔루션 레벨 기능(예: 시나리오 복사, What-If 시뮬레이터, AI 배분 추천)은 **각 해당 화면 정의서로 보내고 여기서 다루지 않는다**
- **에이전트 제안 형식**: 에이전트가 먼저 제안하고 기획자가 채택을 결정하는 구조로 작성
- **표 항목**: `제안 / 내용 / 사용자 가치 / 상태(미채택·검토 필요·채택)` — 가치를 반드시 함께 적어 왜 필요한지 드러낸다
- 채택된 제안은 본문 규칙으로 승격하고 표에서는 상태를 갱신한다

## 체크리스트

- [ ] **기획 의도**(왜 이렇게 동작하는가)가 각 규칙에 드러나는가
- [ ] 검색의 매칭 방식(부분/완전/접두), 대소문자, 타이밍이 명시됐는가
- [ ] 금액·텍스트 입력의 제한·파싱·부수효과가 추측 없이 명시됐는가
- [ ] 토글/삭제/모드 전환의 부수 효과와 연관 데이터 처리가 명시됐는가
- [ ] 유효성 규칙에 그룹·순차 번호가 매겨졌고 빈 번호가 없는가
- [ ] 엣지 케이스(경계값 =·≥, 상호배타, 중복 카운트)가 빠짐없이 다뤄졌는가
- [ ] 스타일은 토큰/구현 참조로 위임했는가 (px/hsl/grid 문법 없음)
- [ ] 데이터 구조가 실제 구현과 일치하는가 (UI 용어-필드명 매핑 포함)
- [ ] 변경 이력과 버전이 갱신됐는가
- [ ] 데이터 구조에 인터페이스 코드 전문 대신 개념+용어 매핑만 있는가
- [ ] 개선 제안이 이 화면 범위 안의 것만 담고, 제안·가치·상태 형식인가
- [ ] **(Docs용)** 기능 목적이 사용자 관점 자연어로도 읽히는가
- [ ] **(TC용)** 각 규칙이 `조건 → 기대 결과`로 검증 가능한가, 에러 메시지 원문이 기재됐는가
- [ ] **(TC용)** 정상/에러 케이스와 경계값이 양방향으로 도출 가능한가
