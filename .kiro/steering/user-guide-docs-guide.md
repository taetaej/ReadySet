# 사용자 가이드(Docs) 작성 가이드

제품 Docs 콘텐츠 파일(`src/components/docs/content/*.ts`) 작성·수정 시 이 규칙을 따른다.
릴리즈노트(`releaseNotes.ts`)는 별도 가이드(`release-notes-guide.md`)를 우선 적용한다.

## 0. 대전제 — 이 문서는 "사용자"가 본다

독자는 개발자나 기획자가 아니라 **플랫폼을 쓰는 마케터·광고주·대행사**다.
화면 명세서(`plan/spec/*`)·기능정의서를 그대로 옮기지 않는다. 명세서는 개발/TC용 언어이고,
Docs는 "사용자가 무엇을 할 수 있고, 어떻게 하며, 왜 그런가"를 사용자 눈높이로 설명하는 문서다.

> 명세서 → Docs는 **번역**이다. 복사가 아니다.

## 1. 명세서에서 가져올 것 vs 버릴 것

| 가져온다 (사용자 가치) | 버린다 (내부/구현) |
|---|---|
| 기능의 목적, 사용자가 얻는 것 | 유효성 규칙 번호(V1~V10), 그룹(A~D) 체계 |
| 화면 흐름, 조작 순서 | 에러 조건 나열표(조건→에러메시지) |
| 설정 시 지켜야 할 규칙 | 데이터 필드명(`isFixed`, `allocations`, `satA/satB`) |
| 결과를 읽는 법, 주의할 점 | 산출식·수식(`y=a×(1−e^...)`), 포화함수 계수 |
| 역할별 접근 권한 | 구현 방식(`position:fixed`, 상태 관리, 컴포넌트명) |

## 2. 내부 용어 → 사용자 용어 치환

명세서 용어를 그대로 쓰지 않는다. 아래처럼 바꾼다.

| 내부/구현 용어 | 사용자 표현 |
|---|---|
| 다이얼로그 / 모달 / 바텀시트 | 설정 창 / 확인 창 / 안내 창 |
| 토스트 | 안내 메시지 |
| 프리필(prefill) | 자동으로 채워집니다 / 가져옵니다 |
| @멘션 | 질문 대상으로 자동 입력 |
| 100% Stacked Bar / 누적 영역 / 워터폴 | 차트 성격을 말로 풀어서 ("비중을 한눈에", "증감을 누적해서") |
| delta / 증감 플래그 | "차이를 색으로 표시" |
| dimmed / muted | "흐리게 표시" |
| 비잠금 항목 / 최적화 대상 | "잠그지 않은 항목" |
| 사구간 | "성과가 거의 나지 않는 구간"처럼 풀어쓰기 |

- **전문 용어(KPI·CPM·GRP·도달 등)는 그대로 쓴다.** 쉬운 말로 바꾸면 오히려 전문성이 떨어진다.
  처음 나올 때 짧게 풀어주되(한 줄), 용어 자체는 유지한다. (`ui-design-principles`의 "이해 용이성" 원칙)
- **플레이스홀더 표기 금지**: `{KPI}`, `{단가}`, `{ID}` 같은 치환 변수는 그대로 두지 말고
  실제 예시로 풀거나 "선택한 KPI에 맞게"처럼 자연어로 설명한다.

## 3. "에러 조건표" 대신 "유의사항"

명세서의 유효성 규칙표(`조건 → 에러 메시지`)는 TC용이다. Docs에는 **사용자가 지킬 규칙**으로 바꿔 쓴다.

- (명세) `잠금 ON + 금액 미입력 → "잠금 금액을 입력해 주세요."`
- (Docs) "잠금을 켠 항목은 잠금 금액을 반드시 입력해야 합니다."

규칙의 **이유**가 사용자에게 유용하면 괄호로 덧붙인다.
예: "전부 잠근 경우에는 합계가 총 예산과 같아야 합니다. (남는 예산을 배분할 대상이 없기 때문입니다)"

## 4. 시점에 흔들리는 수치는 박아두지 않는다

- 상품 개수(예: "228개"), 매체별 상품 수처럼 **스냅샷성 수치**는 쉽게 틀린다. 적지 않는다.
  대신 "주요 디지털 매체", "업종에 맞는 상품만 표시" 식으로 둔다.
- 반대로 **정책상 고정값**(최대 90일, 최대 30개, 시나리오명 30자 등 사용자가 지켜야 할 제약)은 적는다.

## 5. 구조 — 다른 솔루션과 통일

솔루션 가이드는 Reach Caster(`reachCaster.ts`)를 기준 포맷으로 삼는다. 페이지 구성:

1. **개요** — "~란?", 핵심 가치, 지원 KPI/매체, 주요 기능, 워크플로우, 접근 권한 표
2. **원리와 개념** — 질문형 도입("예산을 어떻게 나눠야 성과가 좋을까?") + 핵심 개념을 사용자 언어로
3. **시나리오 생성** — Step 1~3 흐름, 입력 필드 표(항목/필수/설명/제한), 설정 시 유의사항
4. **시나리오 관리** — 목록 조회·검색·필터·정렬, 복제/이동/삭제
5. **시나리오 결과** — 화면 구성, 각 영역(스코어카드/차트/테이블) 읽는 법, 참고 사항

- 섹션 제목은 **짧은 질문/구**가 강하다. (`ui-design-principles` 참조)
- 접근 권한은 역할(Marketer/Client/Agency) × 기능 표로 끝에 둔다.

## 6. 이미지 자리

화면을 설명하는 위치에 이미지 자리를 Reach Caster와 동일 문법으로 둔다.

```
![설명|비율](/docs/images/{솔루션-slug}/00X.png)
```

- 폴더: `public/docs/images/{솔루션-slug}/` (`.gitkeep` 포함). slug는 섹션 `id`와 동일(예: `budget-optimizer`).
- 번호: 화면 흐름 순서대로 `001`부터. 생성 흐름 → 결과 흐름 순.
- 비율: 작은 버튼류는 `30%`, 전체 화면/차트/테이블은 `100%`.
- 실제 이미지가 없어도 자리는 미리 잡아둔다. 파일만 넣으면 바로 렌더링된다.

## 7. 메타 필드

각 페이지 객체는 다음을 갖는다.

- `id` / `slug` — 케밥케이스, 섹션 prefix 통일(예: `budget-optimizer-result`)
- `title` — 사이드바에 뜨는 짧은 이름
- `updatedAt` — `YYYY-MM-DD`. 내용 변경 시 갱신
- `content` — 마크다운 템플릿 문자열. 백틱(`` ` ``)과 `${}`가 깨지지 않게 주의
- 준비중 솔루션은 `disabled: true` + `disabledLabel: '준비중'`로 두고, 정식 공개 시 전용 콘텐츠 파일로 분리하며 `docsData.ts` import를 교체한다.
